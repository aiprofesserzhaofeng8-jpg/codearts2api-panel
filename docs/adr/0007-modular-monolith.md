# ADR 0007：面向多平台扩展的模块化单体

- 状态：设计稿；尚未实施工程迁移。
- 日期：2026-11-01。
- 完整设计：[项目结构设计 v1](../architecture/README.md)。

## 背景

项目已从单 CodeArts 网关扩展为多平台账号池，包含分组模型映射、三种客户端协议、独立策略、预算账本和成长任务。平台接口已有基础，但 Server、Store、CodeArts Account 与前端主脚本承担的职责继续增加。

目标是让新增平台、页面和业务能力有明确归属，同时保留现有协议、并发、凭据与计量保证。单纯移动目录不能解决这些依赖；一次性重写又会失去已有验收依据。

## 决策

1. 一个仓库，一个 Go 模块，根目录区分 backend/frontend；开发独立构建，生产嵌入页面并运行单 Go 服务。
2. 业务职责、数据归属和依赖规则按架构文档执行。最小平台注册表与可选能力继续使用；平台不拥有全局权限、预算或重试。
3. 权限复核、选择实际型号与账号、取得租约由一个准入协调器原子完成；scheduler 提供纯选择算法，不引入独立放行计数器。
4. HTTP 与业务分离，持久化与运行状态渐进分离；移出旧锁和改变存储格式各自作为独立阶段验证。
5. 前端使用 Vue/TypeScript/Vite，按页面迁移。最初保留既有主题和交互，复用公共表单与校验。
6. 文件存储继续作为首个实现；多用户和多实例是另外的能力，不因为引入数据库就宣称已支持。
7. 工程布局、业务重构和新产品能力分别交付，已有未提交功能先形成可追溯基线。

## 取舍

模块化单体保留简单部署和进程内调用，但要求明确维护包依赖和原子事务。独立前端增加构建工具与依赖管理成本，换取组件复用、类型检查和页面开发体验。阶段迁移存在临时兼容 wrapper，必须记录其退出条件并删除重复实现。

暂不采用微服务、动态插件、通用工作流引擎、多 Go 模块或多个可变配置中心。出现实际独立部署、隔离故障或插件分发需求时重新评估，不用预设架构承担目前不存在的运行成本。

## 生效方式

本 ADR 记录设计选择，不证明任何新目录或功能已经实现。实施提交按 [迁移计划](../architecture/MIGRATION.md) 更新阶段状态与证据，完成相应阶段后再将设计状态更新为已采纳/已实施。支持文件与源码目录按需要逐步落地。
