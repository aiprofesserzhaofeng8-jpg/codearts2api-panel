# 码道 DeepSeek V4.1 Flash：量化、上下文和缓存核验

## 已取得的证据（2026-10-26）

这些测试直接请求码道国内上游 `snap-access.cn-north-4.myhuaweicloud.com/api/v2/chat/completions`，固定一个有效账号，使用合成数据，不改变账号池或 Pi 配置。

### 量化精度

上游模型目录返回 `provider=internal`，没有 quantization、precision、dtype 或权重量化版本字段。它们不能证明 INT4/INT8/FP8/BF16 中任何一种。模型自报、回答风格、首 Token 耗时和短任务准确率都不能鉴定权重量化精度。开源权重的配置也不等于华为实际部署配置。

结论：**未知，需要供应商披露或部署端信息。**可以测任务质量，不能把质量测试结果命名为“量化版本检测”。

### 上下文长度

- DeepSeek 官方 API 的模型页标称 1M 上下文。
- 码道 IDE 文档区分模式：DeepSeek V4.1 Flash 在智能问答中为 1.05M，在智能体/自定义智能体模式中为 202.8K。文档里的 IDE 压缩阈值不必然是直接上游 API 的硬限制。
- 当前中转使用 `x-ot-function=agent-general`；模型目录未提供可确认的上下文上限，不能直接套用官方 API 的 1M。
- **本次实测：65,918 输入 Token + 106 输出 Token 正常完成，并准确找回开头、中间、结尾三个随机标记。**这证明本次请求可用，不证明 200K 或 1M 的最大容量及长上下文任务质量。
- 最初测试时 Pi `codearts-local` 配置为 `contextWindow=32768`、`maxTokens=8192`。随后定位到长会话输出预算被压缩的问题，已将 DeepSeek 的 `contextWindow` 改为 `65536`，`maxTokens=8192` 保持不变；这仍不是上游最大上下文的声明。

原始脱敏结果：`../../artifacts/deepseek-context-check.json`。

### 缓存命中

同账号、同模型、相同请求设置，连续发送 4 次；请求之间间隔 5 秒，每次输出限制 128 Token。

| 请求 | 输入 Token | 上游报告缓存 Token | 命中率 |
| --- | ---: | ---: | ---: |
| 新生成前缀 | 7403 | 未返回缓存字段 | 不作确定判断 |
| 完全重复 | 7403 | 7168 | 96.83% |
| 保持前缀，只改末尾问题 | 7400 | 7168 | 96.86% |
| 在开头加入不同前缀 | 7418 | 未返回缓存字段 | 不作确定判断 |

字段路径：`usage.prompt_tokens_details.cached_tokens`。

证据支持当前码道上游可进行前缀缓存。未返回缓存字段不等同于供应商明确报告 0；本轮不证明缓存 TTL、跨账号共享或每次调用必然命中。延迟未稳定降低，不能用“更快了”替代实际缓存字段。

原始脱敏结果：`../../artifacts/deepseek-capabilities-check.json`。

附加发现：码道模型目录返回自身的 cache_price 和峰谷时间信息，其中缓存参考值与 DeepSeek 官方独立 API 价格表不同。二者不要混算成华为实际费用；中转 USD 价格表依然只是参考估算。本轮有其他客户端在途请求，因此不使用余额变化推导积分兑换率。

## 交给 Pi 的后续执行指令

你要验证的是“当前中转在当前账号上的实际能力”，不要声称鉴定未知量化精度。复用同目录 `PI-DEEPSEEK-1000-CREDITS.md` 的独占账号、记录、脱敏和预算规则，但**不要与积分工作负载实验并行执行**。

### 准备

1. 固定一个账号和 `deepseek-v4.1-flash`，确认无其他客户端在使用账号。不要依赖账号池粘性保证永不换号。
2. 只用随机生成的合成记录和无敏感信息的测试文本。
3. 原始请求测试必须用脚本调用模型 API，不能只把长文件交给 Pi：Pi 自己可能先压缩上下文。
4. 若工具需要调用密钥，让用户通过安全环境变量 `CODEARTS_API_KEY` 提供；程序仅在内存中读取，不打印、不写文件、不将密钥拼入命令行，不读取账号凭据状态文件。环境变量不存在时先说明缺少访问条件。
5. API Base URL：`http://127.0.0.1:10087/v1`。使用 `/chat/completions`，`stream=true`，`stream_options.include_usage=true`，每次 max_tokens 设为 256。累计预算沿用 100 积分软目标与 30 分钟上限。

### 上下文测试

- 先测约 16K、32K、64K 输入，再按预算决定是否测 128K、接近 192K；以响应中的 prompt_tokens 为真实长度，不按字符数充当 Token 数。
- 文本中在 5%、50%、95% 位置插入不同随机键值，要求按顺序提取；每次都核对正确性。
- 超过 192K 的探索需要先报告当前消耗与结果，由用户确定是否继续；不自动发送 1M 输入。
- 记录 HTTP 状态、错误代码、真实输入/输出 Token、finish_reason、是否完整找回标记、耗时。
- 收到明确上下文长度错误时，记录上下界；超时、网关 413 或 502 不能直接认定为模型上下文上限。
- 请求成功但标记错误时，只能说明检索未通过，不能单独证明服务端截断。
- 一个点的成功只给出“已验证可用下界”。不要把未测的最大值写成确定结论。

### 缓存测试

- 生成约 8K Token 的新随机稳定前缀，固定 system、tools、模型和账号。
- A：首次请求；B/C：完全相同请求（分别等待 5 秒、20 秒）；D：只改末尾；E：改最开头作为对照。
- 同时保留 usage 的两类字段：`prompt_tokens_details.cached_tokens` 与 `prompt_cache_hit_tokens/prompt_cache_miss_tokens`。如果二者同时存在，要核对一致性，不相加。
- 缓存命中率 = 缓存输入 Token / 全部输入 Token。缺字段记为 unknown，不能编造成 0。
- 不把 output Token 或 reasoning Token 计入缓存命中率。
- TTL 和跨账号实验是另一个变量，基础测试完成后不要自动扩展；需要时单独设计和计费。

### Pi 实际工作负载检查

观察 Pi 工具调用连续两轮是否保持相同的 system/tools 和历史前缀，以及是否频繁发生上下文压缩、换号或模型切换。不要通过读取真实 prompt 日志进行验证；可用合成会话和测试代理只记录长度、哈希及 usage。

为提高命中稳定性，应尽量保持长前缀不变，将新增问题放在末尾，避免在 system 开头插入每次变化的时间或随机值。即使保持这些条件，上游仍可能因路由、缓存淘汰而未命中。

### 报告

分别输出：量化信息（已披露 / 未披露）、官方文档值、Pi 客户端配置、直接 API 已验证下界、检索正确率、各缓存对照组的真实 usage。不得把它们合并成一句“这是某量化的满血 1M 模型”。
