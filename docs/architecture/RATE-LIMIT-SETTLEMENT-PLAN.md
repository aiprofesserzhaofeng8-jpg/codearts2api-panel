# 上游失败不冻结用户预算

## 已采用规则

上游 429、502、缺少用量回执、部分输出后断流，都不因用量不完整而冻结后续请求。
只累计已知用量、扣除已知费用；无法确认的消耗保留在日志，运营方承担无法结算的差额。
请求数仍按现有口径累计。实际余额不足、请求/Token/费用上限、权限与并发限制继续执行。
当前请求准入仍要求取得计价配置，历史缺失价格或部分费用不会形成永久锁。

参考 sub2api 328db26 的 Chat Completions 路径：有结果则提交已有用量，没有结果则跳过该次用量入账；
后续请求依据真实余额和额度准入。

## 实现

- 删除 access.CheckBudget 的 Incomplete/Unpriced 历史标记拦截。
- 删除钱包入口与预留的 ReviewRequired 拦截；换号预留只加上已知费用。
- 删除上一版 RejectedBeforeUsage、RejectionsOnly 和 429 特判结算分支。
- 保留账本和 API 的缺失标记作为诊断字段，页面不再显示“已暂停”“重置后才能调用”。
- 旧记录无需抹掉或重置；升级后旧标记自然失去冻结作用。余额、Token、历史费用原样保留。

## 验收

- 同一用户密钥依次得到 200 → 429 → 200 → 502 → 200；三次成功共 831 Token。
- 缺少回执时钱包预留释放，换号仍可进行，只扣已知费用。
- 密钥、共享预算、套餐和钱包带历史缺失标记时，账本重放后仍可调用。
- 已输出后断流保留未知状态但不冻结；真实 Token 上限耗尽仍拒绝。
- 使用现有部署源码构建、部署并核对服务健康；不重置真实用户账本。

此规则取代上一版“未知消费暂停调用”的计划与历史验收口径。
