## 1. 要达到的效果

客户端读取 `/v1/models` 时立即查询本地目录，再按当前密钥、分组和来源权限过滤。平台同步失败时继续提供上次成功保存的目录，其他平台照常更新。服务重启后先恢复目录，再执行后台同步。

本次采用“本地读取、显式或后台同步、按平台分区更新”。先完成持久化和读取解耦，再加入并行，最后补齐管理页结果展示。

## 3. 当前代码中的问题

| 位置 | 当前行为 | 影响 |
| --- | --- | --- |
| `backend/internal/server/models.go` | `/v1/models` 调用 `RefreshIfStale`，目录超过 10 分钟后同步等待刷新 | 读取目录可能等待上游网络及刷新锁 |
| `backend/internal/catalog/refresh.go` | 外部平台按账号顺序查，同分区首个成功后跳过剩余账号，最后查询 CodeArts | 先遇到慢平台会消耗后续平台的时间 |
| `backend/internal/app/background.go` | 启动刷新共享 60 秒期限 | 后面的平台可能尚未查询就遇到截止时间 |
| `backend/internal/app/app.go` | 每次启动新建基础 Registry | 上个进程发现的平台目录不能直接恢复 |
| `backend/internal/catalog/refresh.go` | 部分成功可返回 nil | 启动日志可能只显示成功，管理端也缺少明确的部分成功状态 |

现有失败保留规则只保护当前进程已有的分区。账号级 `model_snapshot` 已持久化，但它表示指定账号的观察和发布结果，不能直接替代批量刷新的平台目录。

## 4. 目录保存与恢复

### 4.1 保存平台分区的最后成功结果

通过现有 Store 增加可选的平台目录快照字段，按 `provider + scope` 保存。CodeArts 沿用当前空 scope 分区键。每个分区保存平台、地区、模型数据和最后成功时间。

保存数据须完整保留模型身份、上游 ID、协议、能力及推荐参数依赖的信息。`ClientReference` 等当前 JSON 忽略字段需明确编码为目录快照字段，确保重启前后的列表和客户端推荐结果一致。不保存凭据、授权结果或用户可见列表。

目录快照是可重建数据。旧状态缺少字段时正常加载，保留既有内置目录；首次成功同步后建立快照。旧程序若重新保存并丢弃新增字段，只影响目录恢复能力，不改变权限或账本，不为此升级权限 schema。

### 4.2 成功后保存，再发布

单个分区的提交顺序为读取上游、校验结果、Store 原子保存、替换 Registry 对应分区。网络调用在 Store 锁外。保存失败则该分区保持旧目录，并报告保存失败。

发布仍使用现有 Registry，持久化副本不成为另一套路由查询入口。分区提交还需复核来源账号未删除、未停用、未更换身份，防止同步中的旧结果恢复已失效来源。凭据正常续期按既有代际提交约定处理。

### 4.3 启动先恢复

Store 加载后，在 HTTP 开始服务前恢复有效分区，再建立依赖目录的模型策略与路由对象。此过程只有本地操作。后台刷新完成后按分区更新。

快照不包含权限。删除账号、变更分组、停用来源后的权限仍立即按现有规则生效；最后一个关联账号删除后的分区快照需要清理，不能让旧记录在重启后重新成为有效来源。

首次升级没有历史平台快照时，无法凭空恢复以前发现的 129 个模型。应先完成一次成功同步，之后才能验证重启恢复。内置目录和已有账号发布来源继续使用原有路径。

## 5. 读取与同步分离

| 入口 | 改造后的行为 |
| --- | --- |
| 客户端 `/v1/models` | 读本地并按当前授权过滤，不等待任何目录刷新 |
| 普通用户模型页、密钥使用示例 | 继续使用原权限投影，检查调用链中没有同步网络刷新 |
| 启动 | 本地恢复后，由进程后台执行一轮刷新 |
| 管理员批量刷新 | 继续使用现有 POST 入口，等待一轮结果并展示成功及失败分区 |
| 账号池“同步上游模型” | 保持现有单账号入口和账号来源发布规则 |

保留现有“访问时发现目录超过 10 分钟则更新”的使用方式，但改为向进程后台提交一次刷新信号，当前 GET 直接返回。用一个合并信号保证大量 GET 不生成大量任务，已有刷新执行时不再追加重复轮次。失败后的尝试间隔仍按现有 10 分钟规则，单独记录最近尝试时间，不能把失败时间写成成功时间。

后台刷新由应用生命周期管理，服务关闭时取消。移除 `RefreshIfStale` 中独立于调用方的同步 30 秒刷新路径；不增加定时全量扫描、任务数据库或新的管理接口。

## 6. 批量同步按分区并行

### 6.1 查询规则

1. 从当前启用账号生成平台／地区分区任务，CodeArts 也作为独立任务参与调度。
2. 最多同时执行 4 个分区。每个分区开始执行时建立最长 30 秒期限，同分区账号依次尝试、共享该期限，第一个成功结果即结束该分区。
3. CodeArts 保留原有选号及原生 Models 调用，不顺带增加换号重试。
4. 整轮保留最长 60 秒期限，所有子任务继承该期限。排队时间计入整轮期限，不计入尚未开始的分区 30 秒。
5. 成功分区独立保存、发布，不等待失败分区重试；整轮不自动再重试。
6. 到达总期限后不再启动新任务，未开始的分区标记“未执行”，正在执行的分区标记超时。

4 路并发降低串行等待，但不保证任意数量的平台都能在 60 秒内查完。目录读取依靠已保存结果保持稳定，不能把“所有平台均成功”设为整个系统可用的前提。

### 6.2 避免并发更新互相覆盖

保留同一轮刷新协调入口。重复手动刷新复用正在执行的一轮并等待结果，各等待者取消只停止自己的等待，任务由进程控制且受 60 秒上限约束。网络查询并发，分区保存和发布通过同一提交入口顺序处理。

账号探活当前也会更新平台目录，实施时将其成功目录交给同一提交入口。探活失败和新增加的目录保存失败分开报告，不把已成功的网络探活改报为网络失败。单账号快照仍走原有 `SaveModelSnapshot`，与平台目录保持各自含义。

### 6.3 公共参考信息不阻塞模型发现

模型发现使用本轮开始时已有的公共参考信息快照。将公共参考拉取移到分区查询之后，保留其 5 秒上限和现有缓存／失败退避，受整轮剩余时间约束；更新成功后重建相关元数据投影。若整轮已到期则跳过，下次有时间时再更新。参考信息失败不撤销已经保存的模型目录。

并发查询期间不修改共享 reference 指针；保存的推荐元数据须与最终发布结果一致。

## 7. 失败、空目录与统一模型的语义

- 分区超时、网络错误、取消、保存失败均保留该分区上次成功目录。恢复成功后清除该分区错误。
- 保留当前空列表约定：外部平台成功返回空列表时替换为空并持久化，CodeArts 空列表继续作为错误保留旧目录。不得统一把空列表当作成功或失败。
- 单账号同步继续执行“实时发现可发布、漏列保留已发布来源”的约定，批量分区替换不能清空账号独有的 `Published` 来源。详见[账号模型发布](ACCOUNT-MODEL-PUBLICATION.md)。
- 统一模型继续按现有预设追加缺失来源，保留管理员停用状态、公开名称、别名和分组规则。成功分区发布后执行相应协调，协调失败单独显示，不回滚其他分区已保存结果。
- 缓存目录表明“上次发现过该模型”，实际调用仍经过当前账号状态、权限和调度检查。同步不能扩大分组权限，也不新增预算、并发或推理限制。

## 8. 返回结果与管理页

复用现有刷新接口及页面，增加整轮状态、分区状态、最后成功时间、错误及模型数量。保留原有 `models`、`provider_errors` 字段，让已有调用方继续读取。

整轮状态区分全部成功、部分成功、全部失败、无可同步账号。有分区失败或未执行时不能显示“全部同步成功”。有成功提交时返回 HTTP 200 并明确整体状态；全部失败沿用错误响应并附带分区结果；无可同步账号作为独立空结果说明，不伪造上游失败。`ok` 若保留，明确表示是否有成功提交，前端展示以整轮状态为准。

页面展示例如“6 个分区成功，1 个超时；超时分区继续使用上次目录”。读取页面不自动执行手动同步。启动日志使用同样的状态分类。

## 10. 验收用例

使用隔离状态和假上游验证，不操作真实分组或消耗推理额度。

| 场景 | 必须满足的结果 |
| --- | --- |
| 保存 129 个模型后重启，上游全部挂起 | 首次 GET 返回此前授权目录，不等待假上游释放；没有同步阻塞读取 |
| 冷启动，没有平台快照 | 原有内置目录及账号已发布来源可读取，成功分区逐步补充，失败分区不伪造历史结果 |
| 一个平台超时，其他平台成功 | 最多 4 个分区并行，快平台结果可先读取并持久化，慢平台保留旧目录 |
| 分区多于并发槽且整轮到期 | 不再发起新的网络调用，未执行和超时分别记录，下一轮可以正常启动 |
| 同分区 A 失败、B 成功 | 按原顺序尝试，首个成功即停，不合并成“所有账号都支持” |
| 大量 GET 与重复手动刷新同时发生 | 只有一轮上游批量查询，GET 不等待刷新锁，不产生无限排队 |
| 某分区保存失败 | 该分区内存和磁盘都保留旧值，其他成功分区可提交，页面明确部分失败 |
| 外部空列表、CodeArts 空列表 | 分别验证替换为空及保留旧值，重启后行为一致 |
| 同步期间删除账号或改变身份 | 过期结果不能重新发布有效来源；当前权限变化立即生效 |
| 批量刷新、账号同步与探活交错 | 写入协调无数据竞争，账号独有来源不丢失，快照和生效目录一致 |
| 统一模型、别名、分组和来源停用 | 客户端名称及权限不被同步改写，隐藏／禁用及跨账号限制继续生效 |
| 公共参考拉取失败或整轮到期 | 已发现目录保持可用，重启保留已保存的元数据，不新增目录请求阻塞 |
| 服务关闭、刷新取消后重新启动 | 后台查询响应取消，旧快照正常恢复，刷新状态不永久卡在执行中 |
| 部分失败后下一轮恢复 | 相应错误清除、成功时间更新，启动日志与管理页显示一致 |

复用现有目录恢复、账号发布、分组权限和首次调用回归。新增用例优先断言网络调用顺序、次数及屏障事件，避免用长时间 sleep 验证并发。对改动包执行 race 检查，对管理页检查实际浏览器交互，并运行 API 类型一致性与相关前端检查。

## 11. 发布与恢复

部署前保存当前版本及状态备份。先通过模拟回归，再部署并确认当前进程版本、目录恢复及管理页同步结果。真实上游刷新按部署验收范围执行，目录成功不等于所有型号已通过推理验证。

若需回退，使用已验证兼容的旧二进制和当前状态，避免用旧状态覆盖新凭据、账本或权限；旧版本可能丢弃新增目录缓存。部署验收记录首次快照是否已建立，未建立时不能宣称重启保留已经生效。
