# 分组、密钥与账号删除联动计划

状态：2026-11-21 已实施、审查并部署到本地服务，验收结果见文末。

## 目标与选定规则

1. 新建 API 密钥必须指定有效分组。普通用户密钥使用用户当前有效分组，管理员密钥必须明确选择。
2. 删除分组不要求先手动解绑用户、密钥和账号。删除后原关联密钥立即失去新请求权限，不能退回全局访问。
3. 删除上游账号时，在同一次事务内移除所有分组对它的引用。
4. 修复已有失效账号引用导致分组无法保存，以及长表单隐藏保存错误的问题。

范围限于关联生命周期、权限状态与必要界面反馈。不新增多分组用户、渠道系统、数据库、协议转换或模型融合规则；不重算账本，不删除真实测试分组。

## Sub2API 依据与本项目差异

参考已核对的提交 `328db26f450edbdf9f8d4344a3ea903ac6396842`：

- [创建密钥](https://github.com/Wei-Shaw/sub2api/blob/328db26f450edbdf9f8d4344a3ea903ac6396842/backend/internal/service/api_key_service.go#L519)：创建服务在传入 GroupID 时才查询分组并检查用户的绑定资格。
- [删除账号](https://github.com/Wei-Shaw/sub2api/blob/328db26f450edbdf9f8d4344a3ea903ac6396842/backend/internal/repository/account_repo.go#L991)：事务内删除 account_groups 关联及账号，提交后处理调度快照。
- [删除分组](https://github.com/Wei-Shaw/sub2api/blob/328db26f450edbdf9f8d4344a3ea903ac6396842/backend/internal/repository/group_repo.go#L865)：清理用户授权和账号关系、软删除相关订阅和组合路由、软删除分组。
- [删除后失效缓存](https://github.com/Wei-Shaw/sub2api/blob/328db26f450edbdf9f8d4344a3ea903ac6396842/backend/internal/service/admin_group.go#L1206)与[分组鉴权](https://github.com/Wei-Shaw/sub2api/blob/328db26f450edbdf9f8d4344a3ea903ac6396842/backend/internal/server/middleware/api_key_auth.go#L445)：保留密钥原 group_id，通过分组不存在/已删除返回 403。

“新建密钥强制分组”是用户本次确定的产品规则，不声称 Sub2API 全部路径都强制分组。本项目采用单实例文件存储，复用 Store 的 saveMu、mu 和原子保存，借鉴行为，不复制其数据库/缓存基础设施。

## 改动前的问题

- RemoveAccountAndSave 删除账号和目录快照，却不清理 Group.AccountIDs；分组保存又拒绝不存在的账号。
- 分组编辑只列现有账号，失效 ID 隐藏在草稿中随表单提交，管理员无法移除。
- 分组删除遇到用户或密钥引用直接拒绝；前端还按绑定密钥数禁用删除按钮。
- 管理员空 group_id 当前意味着全局访问，不能用清空 group_id 实现删除后的解绑。
- UserProfile 当前把分组缺失当成资料错误；删除分组后必须仍能登录查看余额与历史。
- 套餐、订阅快照和兑换码也存在关联，必须在同一设计中处理，不能只改密钥。

## 一、新建和重新绑定密钥

### 正常流程

- 管理员创建表单移除“不分组（全部账号）”，改为必选的“选择分组”；没有可选组时说明先创建分组。
- 后端创建路径在存储事务内验证 group_id 非空且存在；不能只靠 HTML required 或客户端检查。
- 普通用户创建密钥沿用其有效分组，不添加任意指定其他组的参数。
- 管理员重新绑定密钥也必须选择有效组，不允许把已有受限密钥改成空组获得全局权限。
- 普通用户密钥仍跟随用户分组，由用户管理入口重新分配，不单独修改。

### 兼容边界

以下为 11 月 21 日版本行为。11 月 22 日的[密钥分组强制鉴权](API-KEY-GROUP-ENFORCEMENT-PLAN.md)已收紧旧密钥权限。

- 已存在的空组管理员密钥保留当前权限，界面明确标为“旧版全局密钥”。本次不静默停用旧客户端或自动为它们选择组。
- 一旦管理员将旧密钥绑定有效组，界面和 API 都不能再解绑回全局。
- 逐一处理创建入口，包括 admin API、access.Management、Store 创建函数和首次引导 bootstrapAccess。新安装的旧引导路径若仍需生成密钥，先创建不含账号的默认分组并绑定，不能继续生成新的全局密钥；首次初始化和私密 access 文件仍按现有恢复流程验证。
- 保留旧状态读取能力；测试中的旧版全局密钥须通过历史状态夹具表达，不能为让旧测试通过而留出生产创建后门。

## 二、删除分组：原关联失效，历史保留

采用“保留历史 group_id，目标分组不存在即失效”的方式。无需新增软删除表或把所有 group_id 清空；未知/已删除 ID 统一按分组失效处理，不复用已删除 ID。

| 对象 | 删除提交后的行为 |
| --- | --- |
| 分组 | 从可选、管理、调度分组集合移除；包含在组内的账号关联随组移除 |
| 上游账号 | 保留账号和凭据，不删除账号 |
| API 密钥 | 保留原 group_id 与密钥本体；显示“分组已失效”；目录、客户端配置和推理返回 403 |
| 普通用户 | 保留原 group_id、登录身份、余额、历史；提示管理员重新分配分组；不能新建密钥或调用模型 |
| 套餐模板 | 引用该组的套餐停用，保留历史定义，不能新发放或兑换 |
| 用户订阅 | 引用该组的订阅标记 Disabled，保留到期日、用量和不可变套餐快照 |
| 套餐兑换码 | 禁用引用上述套餐的未使用兑换码；保留已使用记录；余额类兑换码不受影响 |
| 历史记录 | 用量、费用、钱包账本、已发生兑换记录保留，不清除历史 group_id |

删除需要在一笔 Store 事务中完成分组移除、套餐/订阅/兑换码状态调整和权限发布；失败必须完整回滚，不出现 UI 报失败但部分权益已停用。

### 请求与恢复

- 对旧 group_id 的每次模型目录、配置导出、推理和原子准入均检查有效分组，返回可识别的 group_unavailable 权限错误；不能因参数缺失、重试或其他协议路径退回全局。
- 用户资料、用量和余额读取与模型授权分离。用户模型页显示“分组已失效，请联系管理员”，不能把 API 失败伪装成正常的 0 个模型，也不能使整个用户中心加载失败。
- 已取得租约并开始的请求正常结束和结算；删除后不允许新的租约或重试。请求归属、预算预留和钱包结算沿用已有记录。
- 管理员密钥重新绑定有效组后，按新组恢复；普通用户重新分配有效组后，旗下密钥随用户更新。原有停用密钥不会被顺带启用。
- 对失效分组的禁用订阅，重新分配用户前使用现有“移除订阅”操作；不要静默覆盖订阅快照，也不要把这个恢复操作作为删除前置条件。余额与累计使用不重置。

### 管理界面

- 不再按绑定密钥数量禁用删除按钮。
- 确认框说明：删除该组会使关联密钥无法调用，相关套餐/订阅不可继续使用，账号与历史用量保留。
- 继续使用 expected_revision；过期编辑器删除返回冲突。
- 用户、密钥、套餐列表一致显示失效状态，失效组不出现在新建/绑定选项里。保留的历史引用不能伪装成一个仍存在的分组。

## 三、删除账号：关联一起提交

在 RemoveAccountAndSave 的现有锁和事务中：

1. 查找账号，准备回滚快照，包括账号、目录快照和受影响分组。
2. 从所有分组 AccountIDs 移除该账号 ID，更新每个受影响分组的 revision。
3. 删除账号和账号目录快照，并提交同一次持久化。
4. 提交成功后重建发布目录、清理调度绑定；失败恢复全部状态。

同步审查旧 RemoveAccount 入口，避免不同删除入口具有不同关联语义。账号停用/暂停不解除分组关系。删除最后一个账号后，该组仍是受限空组，绝不能解释成“全部账号”。

不删除平台型号、全局别名或统一模型定义：它们可能被其他账号和分组使用。最后一个来源消失时按既有规则报告不可用。

并发语义：删除更新组版本后，旧表单保存返回版本冲突。即使客户端伪造最新版本，提交已删除账号仍被拒绝。

## 四、修复已有坏引用与保存反馈

- 分组编辑器同时展示现存账号和草稿中失效的账号 ID，后者标记“账号已删除”，允许取消选择或一键移除失效项。只清理确认不存在的引用，不把停用账号当成已删除。
- 不在后台启动或读取时悄悄批量改权限。管理员确认保存时，经现有分组事务提交清理后的 ID 与模型授权。
- 保存错误固定显示在操作区，成功才关闭；失败保留账号选择、模型授权和来源范围。
- 明确区分版本冲突、失效账号、模型授权校验失败和磁盘保存失败；必要字段定位到对应区域。
- 保存后重读已提交数据，并通过普通用户目录及同组密钥验证模型授权生效，不以按钮关闭作为完成证据。

## 验收矩阵

测试使用隔离状态和假上游，不删除真实 test 组，不使用真实密钥发起付费调用。

贯穿验收：临时建 A、B 两组，各授权一个不同的模型。普通用户归属 A 后，先验证客户端能列出并调用 A 的模型、不能调用 B 的模型；保持密钥绑定直接删除 A，再用同一把密钥请求目录和两个模型，均应返回 403，假上游不收到这些请求。最后显式将用户改分配到 B（若有失效订阅先移除），验证同一把有效密钥仅获得 B 的授权。这样能区分“删完一律拒绝”与“分组权限确实生效且可恢复”。

- 创建：管理员空组/不存在组被拒绝；有效组成功；普通用户自动使用自己的有效组；无组用户不能创建；新安装引导不再生成全局密钥。
- 兼容：旧全局密钥仍按原契约工作；重新绑定后无法变回空组。
- 账号删除：跨多个组的账号删除后各组不含旧 ID，组版本增加；无关组不变；最后账号删除后无全局放行；重启后结果保持。
- 保存恢复：含失效账号的真实形态夹具可显示并移除坏引用，保存模型授权成功；用户目录和密钥目录一致，假上游调用所授权模型成功。
- 分组删除：带管理员密钥、用户密钥、用户、套餐、订阅及兑换码仍能删除；普通 API、Chat、Responses、Messages 和客户端配置入口均不得泄漏全局权限。
- 数据与恢复：用户余额/用量可读；历史记录保留；重新分配及移除失效订阅后可恢复正常调用；其他组不受影响。
- 事务：注入保存失败，账号/组/套餐/订阅/兑换码完整回滚；并发删除与旧草稿保存不恢复引用；在途结算无丢失或重复。
- 浏览器：无组创建提示、分组删除确认、失效状态、固定错误位置、长表单和窄屏可用。
- 按影响运行 storage/access/server 定向测试、相关前端 E2E、类型检查、API 类型同步检查、构建及仓库要求的检查。实际结果记录在文档末尾，不能提前标记通过。

## 发布与本地部署

实现和验收完成后再生成升级包。部署前核对当前运行版本并保留其已有修复，避免把落后工作区整体覆盖到运行服务；备份程序和最新状态。包内状态兼容性必须由重启测试确认，不为省迁移而忽略新持久化字段：本计划优先使用已有字段和缺失分组的拒绝规则。

常规程序回滚不得恢复旧账本或旧凭据。删除操作本身不是靠回滚程序撤销；重新分配应走管理接口。真实组的删除和历史引用清理应由用户明确选择对象，功能部署不自动删除或改权。

## 本地验收结果

- 以本地运行版为基线构建 `v0.4.23-local.20261121160821`，发布候选通过 `make check`。从升级包提取二进制，在独立目录运行分组、普通用户和密钥接入三组浏览器验收，全部通过。
- 普通用户的同一把密钥在 A 组可以调用授权模型。删除 A 后，目录、推理和密钥配置入口返回 403。改配 B 后，该密钥可以调用 B 的模型，原模型继续受限。模拟上游记录验证被拒请求未发往上游。
- 删除跨组账号后，重启读回的成员与分组版本正确。浏览器验收覆盖手动移除历史失效账号、保存后重读、带绑定密钥删除分组，以及普通用户失去分组后访问资料和用量。
- 写盘失败时分组和关联权益完整回滚。在途请求跨越成功删除时，原租约释放、余额和用量结算一次，后续申请新租约和预留额度均被拒绝。
- 本地 10087 服务切换后为 running，健康检查返回 8 个就绪账号、129 个模型。运行页面的前端构建标识与发布包一致。发布源码、检查日志、浏览器结果和升级包位于本机 `/home/white/backups/codearts2api/group-lifecycle-gPESDh6h/`。
