# 模型上下文与输出参数动态化计划

状态：目录合并和策略样例已实现。隔离管理接口已验证五个来源的保存、列表与配置导出。实际实例迁移、部署与 Pi 同步待完成。

日期：2026-11-23。

## 1. 改完后的使用方式

模型参数通过“同步上游目录／公共规格 → 保存本地快照 → 客户端读取”更新。管理员可以在现有模型策略中覆盖上下文和最大输出；修改参数不需要重新编译网关。

对 TeleAgent 这种没有公开规格对应项的入口，把实测工作参数保存为部署实例的模型策略，不再把五个数值组合编译进 `default_models.json`。Pi 等客户端通过现有同步命令更新自己的配置。

推荐复用现有目录快照和模型策略完成本次修改。无需新增数据库、定时任务、侧边栏页面或第二套模型目录。

## 2. Sub2API 的做法与本项目取舍

核对来源：[Sub2API upstream_models.go](https://github.com/Wei-Shaw/sub2api/blob/main/backend/internal/service/upstream_models.go)，重点为 `SyncUpstreamModelCatalog`、`mergeUpstreamModelMetadata` 和 `UpstreamModelMetadataSnapshot`。

Sub2API 同步模型时解析上游元数据，用 models.dev 补齐缺失字段，将可用元数据保存在账号的 `upstream_model_metadata` 快照中。同步保留仍在目录或明确映射中的已有元数据；客户端使用保存后的结果。

本项目对齐其“同步、持久化、本地读取”的方式，但保留两项已经确定的设计：

- 存储继续使用现有平台／地区目录分区，不改造成 Sub2API 的账号数据结构。账号独立模型发布仍走原有入口。
- 保留用户此前要求的 OpenCode 规格优先：精确匹配的 models.dev 数值优先于上游目录建议。Sub2API 是上游优先、公共规格补缺；本计划不把这两个顺序说成完全一致。

代码仍可保留通用兼容默认值、身份映射和必要的历史兼容策略。此次目标是日常更新具体模型参数不再要求修改源码，不是删除全部默认行为。

## 4. 参数来源与覆盖规则

### 4.1 人工配置与自动参考分开保存

- 人工策略：继续存于 `model_policies`，由现有管理接口保存，自动同步不得覆盖。
- 自动参考：继续存于目录分区的 `client_reference`，由目录同步更新。
- 上游原始数值：保留在 `provider.Model`，不改写成公共规格或实测值。

这使管理员能够区分“上游报告了多少”“公共规格写了多少”和“本机选择给客户端多少”。继续使用现有来源说明字段，不新增平行证据系统。

### 4.2 有效参数的计算顺序

1. 已保存的管理员模型策略优先；历史兼容策略沿用既有行为。
2. 没有人工策略时，使用同一精确模型匹配的公共规格参考。
3. 公共参考缺失的字段使用上游目录提供的有效数值。
4. 仍缺失时，使用现有已审核建议或通用客户端默认值，并保持其来源标识。

公共规格查找继续按 OpenCode Zen、OpenCode Go、已有厂商目录的顺序；只使用精确名称及现有审核别名。不能去掉任意版本后缀来猜测型号，也不能因为名字含 `1M` 就填写 1M。

更新自动参考时按字段补齐：新有效值替换旧值，新数据缺少的字段可保留同一身份下的旧值。保留的是旧参考字段，不是把旧的整套最终策略覆盖到新结果上。

统一模型继续按其已授权有效来源计算公共建议，沿用显式统一模型策略的兼容校验。不能取所有平台的最大窗口后宣称每个来源都支持。

## 5. 同步失败和模型变化

| 情况 | 处理 |
| --- | --- |
| 上游目录成功，models.dev 超时或没有匹配项 | 对仍存在且身份不变的模型保留旧参考值；模型目录照常提交 |
| models.dev 返回部分字段 | 合并新有效字段与该模型的旧参考字段，其余继续走既有推荐逻辑 |
| 新模型没有参考值 | 使用上游数值或现有兼容默认，不借用另一个型号的数据 |
| 相同槽位改成了另一型号 | 重新匹配；禁止继承前一型号参考值 |
| 上游目录读取失败 | 保留该分区最后成功目录和元数据 |
| 上游成功结果移除了模型 | 遵循现有目录删除语义，不为保留元数据重新添加模型 |
| 保存失败 | 保持旧内存、旧快照，返回保存失败；不能显示更新成功 |
| 同步期间发生账号删除、身份变化或较新的探活提交 | 沿用现有提交校验，旧结果不能覆盖新状态 |

身份判断至少包含平台、地区、上游 ID，并沿用已有槽位名称核验规则。不能只按统一模型公开名复制元数据。

模型列表、客户端配置导出和普通推理仍读取本地数据。本次不增加请求时查询 models.dev，也不改变现有批量同步并发数、期限或上游推理超时。

## 6. TeleAgent 五项数据如何迁移

依据：[2026-11-23 实测记录](../acceptance/TELEAGENT-LIMITS-2026-11-23.md)。建议写入精确来源策略：

| 来源 ID | 客户端工作窗口 | 最大输出配置 | 依据 |
| --- | ---: | ---: | --- |
| `teleagent/cn/chat-flagship` | 825737 | 32768 | 成功输入检索与完整输出回执 |
| `teleagent/cn/chat-flash` | 510173 | 8192 | 成功输入检索与完整输出回执 |
| `teleagent/cn/chat-lite` | 761525 | 8192 | 输入有成功记录；输出为人工工作建议，8K 完整生成尚未验证 |
| `teleagent/cn/chat-nano` | 262144 | 32768 | 共享窗口边界推断与完整输出回执 |
| `teleagent/cn/chat-pro` | 510167 | 8192 | 成功输入检索与完整输出回执 |

这里的窗口是工作参数。除 Nano 的边界推断外，其余取成功输入记录；输入、输出来自独立测试，客户端仍需预留输出空间。超时不能证明更大窗口不受支持。

Lite 原先写入的 1024 只是一次完整生成长度，将其固化为默认输出会使长答案过早截断。本计划建议迁移为 8192，并明确记作人工建议，不能标成“实测最大输出”。管理员已显式保存的 1024 或其他值不自动覆盖。

实施步骤：

1. 整理不含凭据的五项部署配置样例，完整策略复用现有构造和校验规则。保留已配置的摘要开关等其他字段，不额外启用摘要。
2. 部署迁移时通过已有 `/admin/api/model-policies` 读取和保存，遵守认证、路由版本及统一模型兼容校验；不直接编辑运行中的状态文件。
3. 对已有显式人工策略的来源跳过并记录，不能将 GET 返回的自动建议误判为人工配置。识别依据使用已有兼容性来源信息，并在测试中核对。
4. 保存失败或与统一模型策略冲突时报告具体来源；已成功项与失败项分别记录，不放宽校验，也不删除原有策略。
5. 确认五项已保存或已有人工策略后，部署移除内置数值的新版本。新安装实例按需应用样例，不在每次启动时自动导入。
6. 更新实测文档的配置接入说明，保留原始测试结果，区分迁移建议和历史实测。

无需为五项迁移新增后端导入 API 或常驻迁移框架；使用现有模型页或管理接口完成。

## 8. 验收标准

使用隔离 Store、假上游及可控的公共规格响应完成回归；已有真实大输入测试不重复消耗额度。

1. 同步参数 A 后重启，未联网即可从模型列表和客户端配置读取 A。
2. 重启后上游目录刷新成功、公共规格失败，同一模型的 A 不退回 32K／4K。
3. 公共规格恢复并返回 B，B 持久化且导出生效；再次重启仍为 B。
4. 公共规格只返回窗口，原最大输出参考保留；反向缺失同样验证。
5. 管理员保存 C 后同步 B，继续使用 C；保存失败仍使用原策略。
6. 槽位身份变化、跨平台／地区同名、模型删除均不错误继承旧参考。
7. 五项 TeleAgent 参数来自保存策略，删除对应内置数值后仍可导出；Lite 的 8192 明确是人工建议。
8. 统一模型的多来源公共建议与显式策略校验继续生效，未授权来源不会影响用户导出。
9. `/v1/models` 与客户端配置入口使用一致参数，读取时不新增网络请求；模型用途、图片和工具能力不因窗口数值而变化。
10. Pi 同步后读取新的 `contextWindow`／`maxTokens`；既有凭据和其他客户端设置保留。网关更新不会自动改写已存在的 Pi 配置。

执行受影响 Go 包、客户端同步脚本的相关回归及并发更新检查。文档阶段不运行推理测试、不部署、不修改用户数据。

## 9. 完成条件

源码验收通过、实例策略迁移完成、部署后快照恢复验证通过、Pi 同步确认四项分别记录。只有更新源码不能称为部署完成，只有更新网关也不能称为 Pi 已生效。

回退优先恢复兼容的程序版本并保留当前状态；不得用旧状态覆盖新的凭据、权限或用量账本。已有显式模型策略在回退后仍应优先生效。
