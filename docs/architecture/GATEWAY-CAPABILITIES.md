# 中转平台能力边界与验证要求

本项目面向多个平台的编码模型，共享公开模型名称。目标不是让每个模型宣称具备所有能力，而是让客户端准确知道可用能力，并把请求交给同时满足这些能力的来源。无法满足时明确报错，禁止丢弃图片、文件、工具参数后继续返回成功。

## 原生型号与平台能力

统一模型的能力以原生规格为上限，同时受授权来源与适配器能力限制。原生支持图片，不代表每个来源均可传图；平台某入口实测能识图，也不能证明同名底模原生支持图片。能力计算和实际请求过滤使用同一份约束。

已核实的精确型号规格保存在现有版本化目录 `backend/internal/catalog/default_models.json` 的 `native_models` 中，每项记录官方参考链接与核实日期。没有新增模型注册中心、状态 schema、管理员逐项配置或请求时网络探测。后缀、Flash/Pro 等变体不能按家族前缀套用。未核实型号保留来源声明，不能标为已核实的原生能力；官方支持也不能补造未知的来源能力或上下文数值。

`/v1/models` 与 `/v1/client-profile` 同时返回 `capability_basis`：`native_and_authorized_sources` 表示已核实的原生上限与授权来源共同约束，`authorized_sources` 表示仅来源证据，`provider_catalog` 表示直接平台入口。可用时附带 `native_model` 供核对；它是官方规格参考，不是该次底模身份认证。

例如共享 `glm-5.3` 按官方纯文本规格声明，不接受图片，返回 HTTP 400 / `native_model_capability_unsupported`；独立的 `glm-5.3-flash` 可在来源支持时传图。完整平台入口 `workbuddy/cn/glm-5.3` 保留其平台服务能力，同时附带原生纯文本规格。用户主动选择平台入口时允许使用平台增强服务，不能把它提升为共享原生能力。自定义统一别名若所有来源指向同一已核实型号，同样继承该上限。

原生文件、视频等能力不因此自动开放。Files API、协议转换、上传与权限隔离仍须独立实现和验证。验证记录见 [原生能力对齐验收](../acceptance/NATIVE-MODEL-ALIGNMENT-2026-11-06.md)。

## 核心能力

| 能力 | 应有行为 | 验证方式 |
| --- | --- | --- |
| 模型目录与统一名称 | 同一型号共享名称，保留精确来源入口；目录存在与账号可用分别表达 | 公共名称与每个原始来源分别调用 |
| 三种客户端协议 | Chat Completions、Responses、Messages；区分原生能力与协议转换 | 每个公开模型分别进行流式及非流式请求 |
| 多轮文本 | 保留 system/user/assistant 语义与历史，不擅自替换内容 | 先前轮次包含随机代码常量，最后一轮要求引用 |
| 流式完整性 | 有真实正文、正确结束事件；错误与断流不能包装成成功 | 校验 SSE、结束原因、错误事件与用量 |
| 图片理解 | 保留图片块，路由到明确支持的来源；客户端配置同步 | 只在图片像素内放随机文字和颜色，检验回答 |
| 图片格式与传输 | base64、URL、格式、大小和图片数量分别有约束 | 分别验证各种传输，不用 base64 成功代表 URL 成功 |
| 工具调用 | 保留函数名、JSON 参数、调用 ID；工具结果关联正确 | 三种协议分别完成流式工具调用和结果回传 |
| 工具返回图片 | 工具结果中的图片能进入下一次模型请求 | 模拟 read 图片工具，验证返回图片中的随机文字 |
| 结构化输出 | 记录 JSON Schema/JSON mode 是否接受；不把一次有效 JSON 当作严格约束证明 | 解析结果并校验样例 schema，严格约束另行验证 |
| 能力元数据 | 图片、工具、上下文和输出限制有证据；未知不等于不支持 | 比对目录、client-profile、Pi 配置及真实请求 |
| 权限与租约 | 用户、密钥、分组、来源授权和并发限制在同一准入入口复核 | 隔离回归覆盖越权、并发、撤销和在途结算 |
| 用量与费用 | 不缺报、不重复结算；缓存、推理和未知用量明确表达 | 保存每次请求用量；和上游账单对账另行进行 |
| 故障恢复 | 鉴权、配额、限流、网络、模型不支持分别处理 | 真实错误分类；断流、取消、切源采用隔离故障注入 |
| 可维护性 | 健康检查、版本、日志、升级、备份、恢复 | 现有部署验收，不用一次聊天代替维护验证 |

工具代码通常由客户端执行。中转平台传递工具定义、调用和结果；浏览器、命令执行、文件读写或 MCP 是否运行，由客户端或专门的执行服务负责。模型会输出一个工具名，不等于整个工具闭环已经可用。

## 文件上传与文件理解

以下四种功能应分别声明，不能混为一谈：

1. **客户端读取 TXT/代码/CSV 后发送文本**：无需 Files API，但有客户端大小及上下文限制。
2. **图片随消息内嵌发送**：属于图片输入，通常也无需 Files API。
3. **文件上传并取得 file_id**：需要上传、查询、引用、删除、权限隔离、生命周期和容量管理。
4. **原生 PDF/document/input_file**：还需要协议转换与实际模型/上游提供文档理解能力；上传成功不能代替理解成功。

未来增加文件功能时，优先建立明确的文件所有者与授权映射、大小/MIME 校验、私有存储和到期清理。对文本文件可以显式提取文本；PDF 可选文本提取或按页转换图片，并明确扫描件/OCR及页数限制。未实现的类型应在执行上游请求前返回明确错误，不能悄悄改成空文本。

截至 2026-11-06 的检查，当前服务没有 `/v1/files` 路由，Messages 转换明确拒绝 document，Responses 的 input_file 存在静默遗漏的实测线索。详细证据与状态见本次验收报告；未进行生产代码修复。

官方参考：[文件 API 与 file_id](https://platform.claude.com/docs/en/build-with-claude/files)、[客户端工具与服务端工具](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)。本项目支持范围以自身实现和验收为准。

## 按产品范围选择的扩展

图片生成与编辑、语音识别/合成、实时音视频、Embedding/Rerank、Batch、原生 Responses 状态存储/WebSocket、服务端搜索/代码沙箱属于独立能力。编码模型中转可以按需要逐项增加，不应只因某个供应商拥有接口就宣称全部支持，也不应把缺少这些扩展当成所有聊天模型不可用。

## 本次全模型测试范围

脚本：`scripts/model-capability-audit.py`。必须显式传入 `--live`；使用已有 Pi provider 或环境变量读取密钥，不在命令参数或报告中记录密钥。测试不修改模型定义、分组、Pi 配置或生产程序，真实调用仍会产生正常用量、日志及健康状态变化。

公开模型按 12 项核心用例测试：三协议各两种文本响应、三协议工具闭环、直接图片、工具读图闭环、结构化输出样例。不可调度、无权限、限流或网络失败后，后续能力标记为受阻，不能据此推断模型不支持。

每个已配置的原始来源还应单独验证文本、流式、工具和图片，避免共享模型经某个健康来源成功后掩盖其他来源不可用。来源测试不保证覆盖同平台下的所有账号。

本次不对每个型号进行上下文极限压测、长期稳定性压测、费用精确对账、所有图片格式/URL/多图组合、并行工具与强制 tool_choice 的全部组合测试。JSON Schema 强制约束也未获证明。未执行的项目应在报告中列为未覆盖，不能把目录中的最大参数当作实测上限。

本次也不通过模型自述判断底模身份。返回测试常量或正确识别图片只能证明本次接口行为；跨平台同型号的身份关系仍需要供应商目录或已确认的配置依据。

全目录批测通过真实网关 HTTP 接口进行。工具由测试侧返回合成文件内容，不执行任意系统命令；不能把该结果称为每个型号都完成了 Pi/Codex/Claude Code 的客户端验收。此前单独完成的 Pi 图片验收保留其独立范围。

复用命令：

```bash
python3 scripts/model-capability-audit.py --live \
  --output artifacts/model-capability-audit/new-run
```

不含密钥的运行快照可以配合 `--source-inventory` 对配置来源验收；`--model` 和 `--features` 可缩小重测范围，`--resume` 复用已完整记录的结果。输出目录应按批次区分，避免覆盖首次失败记录。
