# 模型能力与协议兼容修复计划

日期：2026-11-06，进度更新于 2026-11-07。基线：本机 v0.4.5。状态：R1 范围收缩为附件丢失防护；文件仓库及本地解析已撤回，源码重新验收通过，尚未部署；R2 代码完成，37/39 项真实通过、2 项来源缺失受阻；R3 修复与真实验收完成，待部署；R4 空内容兼容修复与当前验收完成，历史 400 的归因仍未证实；R5 代码与隔离验收完成，4 项真实平台验收受阻；R6 功能与本地验收完成，15 项 Pi 调用中 8 通过、7 个 Kiro 来源受阻。

## 目标与基线

目标：同一原生型号跨平台使用同一个公开名称；能力声明与实际路由一致；图片、文件、工具及历史消息被正确处理；客户端能够识别可用能力和明确的失败原因。

依据：[全目录实测](../acceptance/MODEL-CAPABILITIES-2026-11-06.md)、[原生能力对齐验收](../acceptance/NATIVE-MODEL-ALIGNMENT-2026-11-06.md)、[能力边界](GATEWAY-CAPABILITIES.md)。

已经完成的基线：原生规格约束、模型列表与客户端配置一致性、请求能力校验以及 Pi 配置同步。v0.4.5 的 54 项针对性验证通过，但不代表六类遗留问题已解决。

当前记录：89 个公开名称，15 个具备完整客户端推荐参数；原生规格表包含 13 个精确型号，对当前公开目录中的 11 项提供规格参考。来源能力缺口为 34 个公开名称、39 个“名称—能力”组合，其中工具 32 项、图片 7 项。上述数量是检查时快照，不是固定产品限制。

## R1：文件处理

### R1-A：阻止静默丢失

已观察到 Responses 接收有效 PDF 的 `input_file` 后返回 200，但附件常量没有被读取；转换函数未处理该内容类型。`/v1/files` 上传返回 404，Messages document 明确拒绝。

- 在协议转换入口识别文件内容块和引用，包括 `input_file`、`file_id`、`document`，避免未支持内容被转换为空文本。
- 对未实现的内容类型返回清晰、可识别的请求错误；流式请求也应在提交正常响应前拒绝。
- 保留合法文本、图片、工具结果；检查混合内容和嵌套工具结果，避免只检查首条消息。
- 起点：`backend/internal/responsescompat/chatcompletions_responses_bridge.go`、`backend/internal/server/responses.go`，以及现有 Chat/Messages 转换入口。

验收：三协议、流式与非流式、纯文件及混合内容用例均有明确结果；未支持文件不触发上游请求、故障重试或账号冷却；没有丢弃附件后返回成功的路径。

### R1-B：已取消的文件仓库与本地解析

2026-11-07 按用户确认撤回尚未部署的 Files API、持久化附件、file_id 解析、PDF/文本提取、容量与过期管理，以及 poppler-utils 镜像依赖。原因是这些功能增加数据留存、资源开销和维护责任，超出当前网关范围。

客户端读取文件后发送文本，图片通过已支持的图片输入通道发送。当前文件内容块及引用统一在上游调用前明确拒绝，不宣称原生文档理解或文件存储能力。未来某来源需要原生文件转发时另行确认协议与权限范围。

## R2：补齐来源能力证据

- 从已有 39 项缺口清单逐项核对，保留原始来源正例及共享名称失败记录。
- 使用精确型号的官方规格约束原生能力，再核对平台目录、适配器传输能力与真实测试；不能凭模型名称或自述判断。
- 修复来源适配器遗漏的 `ImageInput`、`ToolCalling` 字段。目录没有声明时，只有具备可维护依据的精确来源才补充证据，不把一次成功推广为整个平台支持。
- 共享请求仍要求同一来源同时满足图片、工具和输出限制；不得删除能力门禁。
- 平台增强服务与原生能力分开表达；官方不支持的能力即使平台测试通过，也不能提升共享原生型号的上限。
- 原生支持但适配器不支持时，记录为传输能力缺口；未知继续保持未知。

验收：39 项逐项获得“已修复、原生不支持、来源不支持、待核实或外部受阻”的证据结论。只有完成共享名称实际调用和客户端配置核对的项目才能标为已修复；工具须验证结果回传后的最终回答，图片须识别随机图像内容。

## R3：Messages 工具历史兼容

上次实测有 7 个共享名称首轮产生工具调用，第二轮被“没有支持原生 Messages 思考与签名的来源”拦截。

- 检查 `RequiresNativeMessages` 对普通推理文本、签名 thinking、redacted thinking 和显式思考控制参数的判断。
- 对可转换的普通推理历史进行明确映射；需要原样保留的签名内容继续限制到兼容的原生来源。
- 工具名称、参数、大整数、调用 ID、结果归属及混合图片完整保留；不得通过删除 thinking 或工具历史绕过问题。
- 起点：`backend/internal/protocol/anthropic.go`、`backend/internal/server/anthropic.go`。

验收：7 个历史失败名称逐项复验，完成“首轮工具调用→客户端结果回传→最终回答”，覆盖流式和非流式。隔离测试覆盖签名不可转换、合法拒绝及跨模型不兼容，不将上游受阻算为通过。

2026-11-07 已完成原修复及验收；随后按用户要求直接复用 Sub2API 的 Messages 消息转换核心并重新通过共享 14/14、来源 7/7、Pi 1/1。固定版本、局部适配与开销见 [复用记录](../acceptance/SUB2API-MESSAGES-REUSE-2026-11-07.md)。部署状态仍单独登记。

## R4：Qoder 工具闭环

已有现象：首轮工具调用合法，第二轮重复同一工具或返回 HTTP 400。底层原因尚未确定。

- 保存脱敏的两轮输入/输出对照，检查工具调用 ID、参数、结果和历史顺序。
- 核对 Qoder `chat_context`、会话标识和重试时的历史构造，确认是否重复追加、遗漏或错误关联。
- 区分转换缺陷、平台协议限制和模型自主重复调用；只对已定位问题修改适配器。
- 使用合成只读工具，不执行模型生成的任意系统命令；同一失败限定重测次数，保留首次失败。

验收：受影响型号能消费工具结果并生成最终回答；协议转换不会制造重复调用。平台明确不支持的路径准确声明，仍无法归因的情况记录为未解决，不能以屏蔽错误代替修复。

2026-11-07 完成空工具历史 content 归一化；当前共享三协议 24/24、Pi Responses 工具 1/1 通过。基线 22/24，对照复现 null 历史下的重复调用。历史 DeepSeek/Kimi 400 本次未复现，其根因仍属未确认项，不算被本补丁证实修复。见 [R4 验收与归因边界](../acceptance/QODER-TOOLS-R4-2026-11-07.md)。

## R5：可用性与故障恢复

此前出现 ChatGPT 上游 429、Kiro 无效或不完整响应、Trae 部分槽位业务错误；部分 Trae 已经恢复。这些是历史观察，实施前需重新核对账号与上游状态。

- 目录存在、能力支持、账号可调度、剩余额度、最近验证结果分别展示；状态附带更新时间与作用范围。
- 配额不足遵循可验证的重置时间；没有重置依据时显示未知，不虚构恢复时间。
- 临时网络错误沿现有重试和健康状态机制有限恢复；鉴权失败、请求错误、模型不支持和配额不足分别处理。
- Kiro 无效响应须检查事件流解析与结束条件，不能将空正文或断流包装成成功。
- 保留用户手动暂停、禁用及权限限制；自动恢复不得绕过这些设置。避免每次打开模型列表都触发付费探测。

验收：隔离故障注入证明临时网络恢复后无需重启；取消与失败释放租约，重复尝试不重复计费。真实配额和平台故障单列受阻状态，不作为代码修复完成的依据。

2026-11-07：已实现只读来源状态展示、合法 Retry-After 传递及 Kiro 空/损坏事件处理，复用既有健康、额度缓存、日志和准入机制。冷却到期恢复、暂停/停用保护、取消/预算/输出后不重放、完整检查与浏览器验收通过。旧版生产服务实测 ChatGPT 429、Kiro 两入口 502、Trae 一个槽位 3003，未部署新代码，真实验收仍受阻。见 [R5 验收与阻塞](../acceptance/SOURCE-HEALTH-R5-2026-11-07.md)。

## R6：客户端参数与模型用途

- 按精确来源补齐有依据的上下文与输出建议，区分官方上限、平台限制、管理员配置和测试观察。
- 共享名称继续使用兼容的客户端建议；现有来源缺少数值时以标明依据的公开资料或默认模板补缺，不把默认值称为实测上限。缺失来源和身份变化保留独立提示。
- 区分通用聊天、专用补全、跳转、重写、图片生成和平台自动路由；客户端导出按实际用途与适配能力筛选。
- 同步 `/v1/models`、`/v1/client-profile`、面板说明和 Pi 导出；更新前备份，保留其他 provider 及用户默认模型。
- 优先处理 GLM-5.3-Flash 等网关已验证但因缺少来源参数不能自动新增 Pi 条目的情况。

验收：每个公开型号都有参数与用途的处理结论；可导出的型号通过实际客户端调用，不可导出的型号给出具体原因。不能以目录可见、HTTP 200 或配置文件生成成功替代生成验证。

2026-11-07：隔离候选快照的 89 个公开名称均有用途与导出结论；15 个可导出、60 个未生成来源参数、14 个为专用或用途未确认入口。原始 profile 读取中有 96 项限流，60 是快照结果，不能作为生产已确认缺参的数量。补充 Flash 三个精确来源的实测建议，四来源共享建议为 32768 / 4096，并保留图片声明；原生官方标签不用于冒充来源上限。Pi 逐项真实调用 8 通过、7 个 Kiro 来源受阻；共享 Flash 的启动器、识图、read 工具闭环及现用 Pi 调用通过。现用 Pi 新增该共享名称及相应压缩设置，备份并保留其他 provider、凭据与默认模型。服务未部署，真实验收受阻部分继续保留，见 [R6 验收](../acceptance/CLIENT-METADATA-R6-2026-11-07.md)。

## 共用实现边界

R6 后续：按用户要求直接复用 Sub2API 的元数据合并与 models.dev 解析函数，现有聊天来源缺少数值不再一律阻止客户端配置；使用公开资料或标明依据的 32768 / 4096 默认模板。历史 R6 的 15/60/14 是当时夹具结果，不是本次修改后的统计。来源、许可与当前验收见 [Sub2API 参数复用](../acceptance/SUB2API-MODEL-METADATA-REUSE-2026-11-07.md)。

- 复用现有 catalog、版本化预设、能力字段和 ModelPlan；不再建立第二套模型注册中心或路由。
- storage 继续唯一负责权限复核、选号、并发占位、预算、凭据和账本；协议适配器不能自行绕过。
- 未支持内容明确拒绝，不静默丢弃，不自动切换成另一个原生型号。
- 动态来源能力与原生规格分开维护；一次识图成功不证明底模身份。
- 健康、能力与客户端参数各自保留证据，不互相推断。
- 支付、返利、Embedding、语音、原生 Responses 存储及 WebSocket 等不包含在本计划中。

## 每批交付与验证

1. 固定版本、来源清单和复现用例，保存脱敏基线；不覆盖历史失败记录。
2. 完成对应生产代码及有意义的隔离测试，更新接口类型、说明和状态清单。
3. 按仓库要求先构建前端，再运行对应 Go 测试及必要 race 检查，完成 `make check`。本机 Go 使用 `GOMAXPROCS=2 GOFLAGS=-p=2` 限制资源占用。
4. 真实平台测试设置请求次数、超时与输出上限；分别测试原始来源和共享名称，保留 PASS、FAIL、BLOCKED、未覆盖的区别。
5. 图片、工具和客户端导出改动至少完成代表性 Pi 验证；上游配额、登录和网络受阻单独记录。
6. 本机升级前备份，核对实际版本、健康和客户端配置；发布 GitHub Release 作为独立操作，不因本计划自动执行。
7. 每批增加验收记录，更新下表；有未解决问题或受阻验收时只能标为部分完成。
