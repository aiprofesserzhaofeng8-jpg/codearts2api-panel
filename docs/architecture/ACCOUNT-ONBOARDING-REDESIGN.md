# 添加账号：平台选择与授权流程改版

状态：已实现并完成本地隔离验收；未部署到运行服务。见[验收记录](../acceptance/ACCOUNT-ONBOARDING-2026-11-18.md)。

目标：让用户先认出账号所属平台，再选择账号类型并完成授权。桌面首屏固定三行常用平台，英文品牌名配合真实图标；保留现有账号、授权及保存流程。

## 3. 两步流程

### 第一步：选择平台与账号类型

顺序：平台 → 账号类型 → 授权方式 → 下一步。

| 平台 | 可呈现的账号类型 | 路径要求 |
|---|---|---|
| OpenAI | ChatGPT / Codex、OpenAI API | 分别映射已有 OAuth/凭据导入和 API Key 模式 |
| Claude | Claude 订阅、Claude API、AWS Bedrock | Bedrock 使用既有 AWS JSON 表单；不增加 Setup Token 等尚未实现类型 |
| Gemini | AI Studio API、CLI / Code Assist、Vertex AI | 分别使用 API Key、OAuth/既有导入、服务账号 JSON |
| Zhipu / Kimi / MiniMax | 按量 API、现有个人 Coding 套餐 | 保留已实现套餐名称及 scope，不能以布局改动扩大套餐权限 |
| OpenCode | Zen、Go | 分开保存和显示套餐身份 |
| 其他平台 | 保留当前实现的认证方式 | 只有一种类型时用简短摘要，不画一个需要点击的单选卡片 |

账号类型代表接入通道，不把 Free/Pro 等上游查询到的套餐状态都做成手工选择。地区只在适用表单出现；不将地区混入品牌名称。

“浏览器授权”“API Key”“凭据导入”等授权方式根据类型显示，只有一个可用方式时自动确定。类型有多个选择时用等高卡片、最多三列；不显示没有实际实现的模式。

### 第二步：配置与授权

顶部显示可核对的路径，例如 `Gemini / Vertex AI`，再展示该类型需要的配置和授权步骤。

- 账号名称（可选）移到此步；为空沿用现有上游识别名称。
- API Key 类型使用已有专用输入框，复杂云凭据复用现有 JSON 导入。
- 浏览器授权保留既有生成链接、回调/检查、确认保存过程。
- 凭据只留在本次表单内存，不写入 localStorage，不在类型之间自动套用。
- 保留现有付费短推理提示，放在实际触发校验的按钮附近。
- 提交中禁用重复提交；验证或保存失败留在当前表单，保留可重试输入并显示服务端错误；保存成功才关闭并清空凭据。

## 4. 必须处理的交互细节

### 展开和选中

展开区选中后保持展开。用户主动收起且选中项在展开区时，在常用区下方保留一条带图标的“已选：Qoder”摘要，点击可重新展开并定位；不能让选择无迹可寻，也不临时重排常用平台。

重新打开添加窗口按现有重置规则恢复；任何带入已有选择的流程（例如重新授权）必须自动展开该平台。展开时隐藏“更多平台”，仅显示“收起”；收起时恢复“更多平台”。隐藏项不能进入键盘焦点。

### 切换平台或账号类型

第一步无凭据，可直接切换。第二步返回不提交、不自动删除输入；在尚未切换类型时允许恢复原表单。

实际切换到不同类型时，若已有凭据或正在等待授权，使用现有确认样式提示“切换后将清空当前授权信息”；取消则保留原路径，确认后清空输入、停止旧轮询并释放已有授权会话。切换本身不创建新账号、不触发推理。避免重新打开窗口后旧轮询把新选择覆盖。

### OAuth 配置缺失

Gemini CLI 和 Antigravity 依赖部署环境中的客户端配置。未配置不应伪装为平台未支持，也不能给出无法工作的授权链接。

沿用服务端在发起授权时返回的缺少配置错误，在该步骤展示简短的管理员配置指引。若现有接口没有配置状态，不为“提前置灰”另建能力查询或在前端猜测；不把 Client Secret 返回浏览器。

### 协议展示

协议是账号类型的结果，不是用户随意切换的开关。需要时显示只读说明，例如 Vertex AI 对应 Google 原生 API。

上游传输协议与网关对客户端提供的 Chat Completions / Responses / Messages 分开说明。不要暗示选了某种协议，就自动获得图片、工具或其他平台能力。TypeSafe 明确标注“决策接口”，不标记为聊天通道。

## 5. 尺寸、移动端与可访问性

- 桌面弹窗目标宽度860px，宽度不超过视口减32px，高度不超过85dvh；页头和底部操作固定，内容区滚动。
- 平台项高度56px，图标固定占位，图文间距10px，全部左对齐；字体不因名称长而缩小。
- 桌面四列；平板可降为三列；手机两列。三行限制仅针对四列桌面，手机保留同样11个平台和展开入口，允许六行。
- 手机宽度不足以完整显示最长名称时允许两行，统一该断点全部平台项高度；不出现横向页面滚动。360px宽度必须实际检查。
- 更多平台/收起使用文字与图标，不仅显示三个点；设置 aria-expanded、aria-controls，展开后因触发按钮隐藏，将焦点移至展开区的平台；收起后焦点返回“更多平台”。
- 平台选择保留单选语义和可见焦点；支持键盘操作、Escape关闭及关闭后焦点返回“添加账号”。
- 账号类型或方式切换时，尽量保留弹窗位置和滚动区域，避免整窗突然跳高。

## 6. 工程边界与实施顺序

这是账号添加交互重组，不迁移凭据或状态格式。`chatgpt` 等 provider ID、scope、原始型号、分组权限、共享映射、计费和续期语义保持原值。列表显示可将云渠道组织在品牌下，筛选条件仍能独立选 AWS Bedrock、Vertex AI，避免合并筛选后掩盖实际来源。

复用现有 Vue 页面和控制器；遵守 v-once 的 DOM 所有权，不让 Vue 与旧控制器同时修改同一节点。需要的品牌名、排序、图标、类型到现有 provider/scope 的映射集中为一份前端描述，供选择器和列表使用；不创建第二份后端注册表、能力探测系统或模型目录。

实施分三部分，交付为完整添加流程：

1. 品牌描述和本地图标：统一英文名称、图标来源及所有账号管理显示入口。
2. 第一屏布局和类型选择：四列三行、展开/收起、云渠道归类、地区/协议说明与响应式布局。
3. 授权衔接：迁移可选账号名称，补齐返回/切换/取消/失败重试/成功清空行为，完成视觉及现有平台回归。

优先修改现有 [AccountsPage.vue](../../frontend/src/features/accounts/AccountsPage.vue)、[账号控制器](../../frontend/src/features/accounts/controller.js)、[授权控制器](../../frontend/src/features/accounts/providers/controller.js)、[授权组件](../../frontend/src/features/accounts/providers/ProviderAuthorization.vue) 及对应样式/i18n/测试。不借本次改版增加配额控制、预热请求、自动排序、收藏、搜索或调度策略。
