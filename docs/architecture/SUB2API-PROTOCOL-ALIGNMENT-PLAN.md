# 对齐 Sub2API 的协议路由与转发计划

状态：源码实施与本地验收完成，已升级本地服务，尚未推送或发布 GitHub Release。验收与兼容差异见 [实施验收](../acceptance/SUB2API-PROTOCOL-ALIGNMENT-2026-11-17.md)。

## 目标与边界

保留 `/v1/chat/completions`、`/v1/responses`、`/v1/messages` 和现有别名，按 Sub2API 的规则选择上游协议：同协议直接转发，跨协议才转换。统一模型继续使用同一公开名称与来源集合。

本次只改协议组织：不重写模型融合、分组权限、账号调度、凭据刷新、预算、计量账本或重试框架。不新增平台，不扩展套餐权限，不增加新数据库、第二份模型目录、每请求能力探测或通用插件框架。不把协议选择优先级变成新的来源调度优先级。

现有 `previous_response_id`、`store=true`、后台任务、WebSocket 等限制保持；解除这些限制需要独立的会话归属设计，不随直通顺便开放。TypeSafe 决策接口保持独立。

## 现状与复用基线

现有融合职责已分离：catalog 解析公开名称与筛选来源，storage 在同一事务内复核权限、选号与占位。相关重试、能力过滤和输出后禁止重放测试已通过，不将这些保护当作待修缺陷。

本次要替换的是 Responses、Messages 入口提前转为内部 Chat 的组织方式。现有图片/工具筛选、提示词和用量处理部分依赖该中间格式，需要同步接上原始协议。

固定参考 Sub2API 提交 `ba81c7fd758e425d67f856d601147ef0c5263d3f`，与本项目现有 Responses 兼容库来源一致。实施中不跟随 main 漂移；确需补充其他提交的修复时，只引入相关差异与对应测试并记录来源。

| 参考文件（Sub2API `backend/internal/`） | 采用方式 |
|---|---|
| `service/provider_profile.go` | 复用平台、账号模式、协议端点与路由方式的定义和已核实数据，适配本项目 provider ID/scope |
| `service/upstream_protocol_routing.go` | 抽取纯协议判定、模型协议集合及优先级逻辑；移植对应测试 |
| `service/model_protocol_catalog.go` | 复用 `supported_endpoints` 解析和规则优先级，接入现有目录刷新；不照搬独立缓存/后台刷新机制 |
| `service/openai_gateway_chat_completions_raw.go`、`gateway_anthropic_passthrough.go`、`openai_gateway_passthrough.go` | 抽取同协议请求与响应处理；平台鉴权、HTTP 传输、错误分类和计量回调接本项目已有入口 |
| `pkg/apicompat/` | 已有函数继续使用；缺少的转换器和测试按需直接复制，不再另写同等实现 |

来源链接：[固定版本](https://github.com/Wei-Shaw/sub2api/tree/ba81c7fd758e425d67f856d601147ef0c5263d3f)。逐文件记录直接复制、抽取或适配及差异，保留对应许可证和署名，更新既有 `UPSTREAM.md`；不覆盖本项目已有的工具参数、大整数和原生历史保留修复。

## 目标请求链路

```text
客户端路径 → 原始协议请求与能力需求
                    ↓
         现有统一模型解析、候选来源筛选
                    ↓
         现有原子权限/预算复核、选号及占位
                    ↓
         选定账号和实际模型的上游协议判定
                    ↓
         从原请求准备本次尝试、应用原有策略
                    ↓
         同协议转发 / 按需跨协议转换
                    ↓
         客户端格式响应、现有用量与结算
```

协议判定只选择端点，不选择账号或执行网络请求。候选筛选提前排除无法承载请求功能的来源；选定账号后复核该账号模式的实际端点，不能发送后才发现本地已知的不兼容。

对齐 Sub2API 的判定顺序：

1. 固定协议按账号设置执行，且必须是该模式支持的端点。
2. 自适应、按入站分流的平台：有同协议端点就使用；否则按参考实现回落 Chat。回落转换必须能表达本次请求，不能丢弃功能以求成功。
3. 自适应、按模型分流的平台：管理员显式规则、上游模型目录、内置规则按参考优先级形成协议集合；包含入站协议就直通，否则使用集合首选协议。
4. Google、AWS、Kiro 等专用传输仍由平台适配器处理，不伪装为普通三协议 HTTP 接口。

## 实施顺序

### P1：接入协议选择和原始请求

- 复用协议标识、profile 与 resolver，放入现有 provider/protocol/catalog 职责内，不建立第二份平台注册表。
- 三个入口保留原始请求与协议；分别提取图片、工具、输出限制、原生历史等必要的能力需求，继续交给同一个 `ModelPlan` 筛选。不要为此创建另一套完整消息格式。
- 扩展现有单次执行边界，使其能携带协议与原始响应事件；旧 Chat 调用入口及使用条件保持可用，不要求尚未迁移的平台实现新接口。
- 元数据、静态规则沿用现有目录所有权；API 类型或持久化字段只有确需新增时才变更，不为协议选择预先做 schema 迁移。

完成条件：复用的协议判定测试通过；既有融合、权限、能力筛选与 Chat 路径保持通过。

### P2：同协议直通与必要转换

- 先接 Claude Messages、ChatGPT/Codex Responses 和已有 Chat 上游。普通请求与流式/非流式响应均走对应协议实现，不再经过 Chat 往返转换。
- 复用 Sub2API 转换器接跨协议路径；转换方向由“客户端协议 × 实际上游协议”决定，不由公开模型名称决定。
- 用量从各协议原始响应中提取，投影到现有计量入口；不为了计量将整个 SSE 转成 Chat。保留缺失用量、流错误、取消及已输出后的原有处理。
- 提示词准备/恢复、摘要识别和完整性检查接入协议感知路径，保持适用范围、调用次数与预算复核顺序；不能以直通绕过策略，也不向其他平台扩展摘要能力。
- 统一名称只改响应约定中的模型字段，不清洗工具参数、签名或原始内容。换号时从原始请求重新准备，重选本次上游协议；已经提交输出后继续禁止重放。

完成条件：同协议用例证明未经过跨协议转换，原生字段与事件得到保留；跨协议、计量、策略和融合回归通过。删掉已被替代的重复转换分支，保留仍有调用者的兼容入口。

### P3：对齐现有多协议平台与账号选项

- DeepSeek、Kimi、MiniMax、Zhipu：复用对应 profile，按当前账号模式和地区使用可用端点；有明确不支持的字段或模型时拒绝，不扩大套餐范围。
- OpenCode Zen/Go、Command Code：复用模型协议集合和选择规则，使用现有目录信息；不把某平台支持三种端点等同于每个模型支持三种端点。
- CodeArts、WorkBuddy、MobileClaw、TeleAgent、Cline 保留现有 Chat 接入；Trae、Qoder、Kiro、Gemini CLI、Antigravity、Bedrock、Vertex 保留专用适配路径。Gemini API 的现有 Chat 兼容通道不在本次扩展新端点。
- 仅给实际支持多协议的账号类型补充协议设置，复用现有新增/编辑与保存流程。选项、可用值和缺省语义对齐固定版本 Sub2API；本项目原有缺省路由若不同，缺字段时保留旧语义，显式保存后才应用新选择，并在来源记录中说明这一兼容差异。
- 不增加“每个统一模型固定一种协议”的设置，不重做账号选择器或模型融合页面。必要的前端类型同步使用现有 OpenAPI 生成流程。

完成条件：配置保存/重读与实际请求端点一致；旧账号无需重新登录或导入即可继续使用，三入口仍能调用同一授权公开名。

### P4：整体验收与交付

优先复用 Sub2API 的相关用例和现有测试，只补以下改变契约的缺口：

| 验收项 | 必须证明 |
|---|---|
| 同协议与跨协议 | 对实际支持的方向验证端点、请求体与响应事件；流式和非流式均可用 |
| 原生内容 | 工具 ID/参数大整数、思考签名、拒绝、缓存用量和终止事件不因改造丢失 |
| 模型融合 | 同一公开名三入口、来源切换、实际型号计费、公开名回写及原始型号直调保持 |
| 能力与权限 | 原生功能只进入兼容且授权的来源；没有候选时明确失败，不删字段或扩大授权 |
| 故障和策略 | 换号从原请求重建；首段后不重放；取消/错误/缺用量处理与提示词、摘要边界保持 |
| 配置与页面 | 旧账号缺省兼容；新协议选项保存、失败重试、端点映射及实际页面可用 |

按改动范围执行 Go 定向测试、前端检查及相关浏览器回归；收尾执行仓库要求的 `make check`，涉及共享状态/并发路径时补对应 race 检查。假上游验收不冒充真实平台验收；真实登录、共享凭据刷新或付费推理按明确授权范围执行。

交付包括可运行代码、复用来源记录和验收结果。提交/推送、Release、运行服务升级分别按授权执行并记录，不用源码完成代替部署完成。P1–P3 是实施批次，整体功能以 P4 通过为完成。
