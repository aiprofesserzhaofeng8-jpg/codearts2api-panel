# WorkBuddy 图片输入与网络恢复

## 本次确认的问题

1. WorkBuddy 原生适配器会保留 Chat Completions 的 `image_url`，并没有主动删除所有图片。但读取 `/v3/config` 时没有保存上游 `supportsImages`，对外目录及客户端推荐缺少图片能力；Pi 启动器还把所有模型固定成 `input: ["text"]`，可能使客户端在发送前丢弃图片。
2. Messages 的普通图片能够转换，但 `tool_result` 内的图片原来被序列化为普通 JSON 文本。模型收到的是文本，不是真正的图片内容。无效图片和部分其他媒体块也会被静默略过。
3. 普通 DNS/连接/断流异常进入通用账号失败累计，达到阈值后触发账号熔断。下游连接写入还没有单次写超时；停止读取的客户端可能长期占用账号和密钥并发名额。

这些是代码与隔离回归确认的缺陷。尚未取得用户出问题那次的具体模型名、客户端提示和请求记录，不能据此把每次多模态失败或网络卡住都归为同一个原因。

## 修复行为

- 从 WorkBuddy 的实际 `supportsImages` 字段区分支持、不支持和未知，向 `/v1/models`、`/v1/client-profile` 输出 `supports_images` 与 `input_modalities`。未知不按型号名猜测。
- Pi 启动器根据推荐能力写入 `input: ["text", "image"]`。旧配置需要重新运行启动器生成；仅升级网关不会自动改写已有客户端配置。
- 分组统一名只有全部可用来源明确支持图片时才声明支持；混入文本来源不能把整个组宣传为视觉模型。
- Messages 工具图片保留为 `image_url`，先完成工具结果消息，再携带图片继续会话；图片不会写成 JSON 字符串。无效图片和未接入的文档/音视频块返回明确错误，避免静默删除后生成误导答案。
- 网络传输错误不再累计账号失败或触发账号熔断；请求仍受原有限次重试和总超时约束。已输出内容不能重放，失败后释放账号租约。
- 请求体每次读取及下游每次写入/Flush 有 30 秒期限；失败取消同一次请求并释放并发名额。请求体读完立即清除读取期限，因此正常长时间思考不受上传期限影响。

## 限流设置

三种情况需要区分：

| 情况 | 处理 |
|---|---|
| 本地按密钥 QPS/并发限制 | 可在「配置 → 限流 → 启用按密钥限流」关闭，保存后立即生效，无需重启 |
| 上游明确返回 429/模型额度限制 | 保留上游错误与已有短期冷却；删除本地限流不能让上游取消限制 |
| 网络中断、连接失败、下游卡住 | 本批修复恢复及释放，不再把普通连接错误累计成账号失败 |

若升级前已经进入旧冷却，可对对应账号执行一次清除错误；本次修复不擅自清除现有真实限流或失效凭据状态。不是要求以后每次网络故障都手动恢复。

## 验证范围

模拟上游验证 Chat Completions、Responses、Messages 的图片转发，流式/非流式及工具结果图片共八种组合。另验证上游能力字段、统一名能力交集、客户端输出、网络连续失败后不需清错的下一请求、写入/Flush 失败取消和期限清理，真实 TCP 停止上传/接收时的中断。未使用真实 WorkBuddy 账号执行图片推理；实际型号是否具备视觉能力仍以上游目录及真实调用为准。
