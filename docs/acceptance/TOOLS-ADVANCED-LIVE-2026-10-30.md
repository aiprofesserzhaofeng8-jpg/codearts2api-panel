**确定缺陷：Messages 流式串接两个工具的参数**

三个平台的 `/v1/messages`、`stream=true` 并行工具场景均出现同一现象。模型请求两个工具，但客户端只收到一个 tool_use 内容块，参数增量被拼成：

```text
{"path":"left.txt"}{"path":"right.txt"}
```

这不是有效的单个工具参数 JSON，客户端不能安全执行后续工具。验收客户端在解析参数时立即停止，没有执行错误调用或发起接续请求。外层接口 JSON/SSE 事件本身仍合法，因此该缺陷不属于此前只检测非法响应 JSON 的修复范围。

定位在 `internal/server/anthropic.go` 的 `anthropicStream.consume` 和 `openBlock`：consume 会更新 toolID，但 openBlock 发现 kind 仍为 tool_use 就直接返回，不创建第二个内容块；后续参数又使用当前同一个块索引。结构中也没有为多个上游 tool index 维护独立输出块。这里只记录修复方向：按工具 index/ID 分别管理内容块及参数，保持原有逐事件转发与已输出后不重试的规则。

为排除模型或测试客户端因素，用临时 Go overlay 注入一个固定的两个工具分片序列，分别经过六条生产处理路径。本地竞态回放结果：

| 接口 | 非流式：工具数 / 参数合法数 | 流式：工具数 / 参数合法数 |
|---|---|---|
| Chat | 2 / 2 | 2 / 2 |
| Responses | 2 / 2 | 2 / 2 |
| Messages | 2 / 2 | **1 / 0** |

该诊断测试的断言刻意验证“当前错误能够复现”，日志中的 PASS 不代表缺陷已修复。overlay 不修改工作区或运行服务，回放不调用真实上游。

**待核实：Trae 一次返回 12 个工具调用**

Trae Messages 非流式的并行场景要求读取 left/right 各一次，实际返回 12 个不同 ID 的 tool_use，左右各 6 次。验收按“必须只有两个调用”停止，没有执行这些重复调用。日志记录只进行一次上游请求，因此它不是网关重试导致的重复请求；本轮没有抓取原生上游事件，仍不能最终判定是上游模型重复生成还是原生适配异常。

该请求设置 max_tokens=640，上游回报 output_tokens=927，说明本次 Trae 请求的输出参数没有体现为严格的已回报用量上限。没有进行实际扣费差额核对，不能将客户端输出参数当作绝对成本承诺。

**五例格式偏差**

**测试方法与实际用量**

连续工具的下一步随机文件名只存在于上一步文件内容中，三次工具结果包含不同随机值，最终要求按顺序返回三值。错误恢复先实际读取不存在的 missing.txt，返回带随机 recovery_path 的 ENOENT，再读取成功文件。Messages 使用 is_error=true；Chat/Responses 将结构化错误作为工具结果文本。并行场景要求同一轮两个调用，使用两个线程实际读取生成的文件，并按调用列表的倒序回传结果，通过 ID 检查左右映射。

工具只读取临时目录内允许的文件，不执行模型命令或任意路径。每次请求最多设置 640 输出 Token；专用 API 密钥设最多 162 次客户端请求。因四个异常场景在首轮停止，实际发送 158 次请求，日志全部匹配 request_id，供应商/模型一致、用量已知、每次仅一个上游尝试。没有自动重试掩盖失败。
