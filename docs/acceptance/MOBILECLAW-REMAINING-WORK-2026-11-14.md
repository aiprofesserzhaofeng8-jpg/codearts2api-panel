日期：2026-11-14。范围：本次 MobileClaw 修复交付及后续验收，不代表整个项目 R1～R6 或其他平台全部完成。

## 一、已经解决

此前扫码账号可查询余额、套餐和模型目录，但三个免费模型生成均返回 HTTP 400 / `model_not_found`。仅补充 `ai-provider` 请求头不能恢复。

## 三、执行顺序与验收步骤

### MC-1：先验证用户实际调用路径

1. 核对 systemd 运行进程、版本、监听端口及状态路径，避免测试到旧进程。
2. 使用现有授权密钥查询可见模型，确认以下精确来源存在：
   - `mobileclaw/cn/glm-5.3`
   - `mobileclaw/cn/glm-5.3-flash`
   - `mobileclaw/cn/deepseek-v4.1-flash`
3. 每个来源执行最小文本请求，覆盖流式与非流式；检查正文、结束事件、错误处理与用量。无法取得用量时明确记录，不能推断为零消耗。
4. 检查现有共享名称映射，再通过 Pi 测试至少一个共享名称。用实际来源日志确认命中 MobileClaw，不能把其他平台成功误算为 MobileClaw 通过。若尚未绑定，不静默修改全局映射。
5. 检查请求结束后的租约释放、请求记录和结算；一条逻辑请求不能重复扣费。

### MC-2：验证真实续期与保存

1. 通过运行服务的既有凭证协调器执行续期，沿用按账号互斥、代际检查和保存事务。
2. 不复制活跃刷新令牌到离线工具轮转，不修改令牌到期时间来制造成功，也不直接编辑运行状态文件。
3. 等待正常续期条件，或使用经确认的已有管理操作；没有合适入口时保持待验证，不临时增加公开刷新接口。
4. 记录脱敏结果：续期是否发生、到期时间是否延长、身份与供应商是否一致、保存是否成功、续期后请求是否成功。不得输出令牌内容。
5. 真实保存结果验证不能用恢复旧备份替代；已轮转的令牌不得回滚为旧值。磁盘失败、并发竞争等破坏性场景继续用隔离测试覆盖。

### MC-3：按来源验证能力

- 图片：仅对有可信能力依据的来源发送合成测试图片；确认图片真实送达且回答匹配，不能仅凭 HTTP 200 或模型自述通过。
- 工具：使用无副作用的测试工具，验证工具名、参数、调用 ID、结果回传和后续回答，覆盖流式参数拼接。
- 多轮：验证历史消息、工具结果和推理字段处理，不丢失、不重复。
- 长对话：明确测试长度与请求预算；普通多轮成功不代表最大上下文已验证，不进行无上限的压力测试。
- 原生不支持的能力不标为缺陷，不通过暗中换型号制造成功。共享名称仍需核对实际来源能力，不能仅凭某一个来源通过就放开全部来源。

### MC-4：处理旧授权

只检查必要的脱敏状态，不批量导出凭证。新授权正常的账号保留；缺少绑定的旧账号在修复版本中重新扫码，使用对应手机号的蜂窝网络完成授权，并明确确认替换保存。多个云账号或多个供应商不自动任意选择。没有独立刷新材料的桌面导入账号仍按原方式重新导入。

### MC-5：交付

先完成 MC-1，并记录 MC-2 的真实进展。正常完整交付以 MC-1、MC-2 通过为目标；如用户决定提前发布，必须明确真实续期仍待验证。发布说明区分源码修复、隔离测试、真实上游测试、运行服务升级四个状态，不把构建成功当作已经部署。保留备份升级方式，不删除用户数据。

## 四、记录格式与停止条件

每项真实测试记录：日期、运行版本、客户端/协议、公开名称、实际平台与来源型号、是否流式、HTTP/业务码、正文或工具断言、用量是否可用、结果及未覆盖范围。公开记录不包含账号身份、Token、API 密钥、原始状态或私人消息。

先串行执行小请求；出现认证错误、配额错误或未知业务错误时保留脱敏证据并停止该分支，不反复重试、不扩展为全平台测试。
