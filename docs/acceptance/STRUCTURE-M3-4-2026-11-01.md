# 提示词恢复与摘要准备分离验收（M3 第四批）

日期：2026-11-01。基线 `22b6c04`，本批版本 `0.3.0-structure-m3.4`。本批只迁移有限的提示词恢复和纯摘要识别/准备；M3 的全局换号、摘要实际执行、凭据归属及管理业务分离仍未完成。

## 变更与保持的边界

- `gateway.RunPromptPolicy` 接收单平台推理配置投影及已绑定的执行回调，不接触 HTTP、Store、账号池或具体平台。`PromptBlocked` 继续使用原错误接口与包装链判断。
- server 读取原平台配置及摘要豁免，再通过两个 hook 提供原有尝试计量和预算/分组权限复核。顺序保持为：结束旧尝试、复核权限和预算、准备替换请求、开始新尝试、执行。恢复最多一次，使用原账号、凭据、型号和租约，不新增上游调用或总重试预算。
- 所有已观察分片均关闭提示词恢复窗口，包括空 delta、用量分片和非流式消费者私下缓存的分片。取消时不进入恢复；未命中恢复的错误保持原对象和分类。
- `requestpolicy.IsSummaryRequest` 和 `PrepareSummary` 持有原 Pi/显式摘要识别及请求准备。工具优先排除摘要，普通用户引用不会误触发；保留原指导文本、调用者较低的正数输出上限、思维控制、原始 JSON 数字及工具数据。无改写的 passthrough 仍借用原请求字节。
- `SummaryOptions` 是两字段的每次调用快照，不复制或迁移持久化 ModelPolicy。原来只供测试使用的客户端默认策略 helper 移到测试文件，生产不保留重复实现。
- 三平台原生协议、Store、页面与基线逐字节一致，状态 schema 仍为 6。摘要的 8MiB 私有缓冲、完整性验收、备用型号选择、重试、冷却和账本均由原实现负责。本批没有新增公共提示词继承或扩大 WorkBuddy/Trae 的摘要能力。

## 性能与本机部署

基线和新版分别编译测试二进制，使用相同夹具。固定不同物理核 CPU 0、2，均设置 `GOMAXPROCS=2`，五轮交替容量测试及五轮交替微基准；每轮每种容量用例 40 次请求、并发 2、固定上游等待 20ms，两段 HTTP 均经本机 socket。全部调用成功，实际上游请求次数等于客户端请求数，峰值并发为 2，剩余租约为零。

| WorkBuddy 非流式 | 23.444ms | 23.429ms | -0.06% |
| WorkBuddy 流式 | 23.035ms | 23.170ms | +0.59% |
