# WorkBuddy / Trae 单次执行分离验收（M3 第三批）

日期：2026-11-01。基线为 `9f4b100`，本批版本为 `0.3.0-structure-m3.3`。本批将两平台的普通单次执行与非流式聚合接入 gateway，整个 M3 的请求编排和 HTTP/管理业务分离仍未完成。

## 变更与边界

- `gateway.StreamTransport` 只要求 `Stream`，`ChatSession` 在其上扩展原生 Chat 和空响应回退能力。WorkBuddy/Trae 不实现虚假的 Chat 接口。
- `upstream.BindStream` 借用原有 Normalize 后的凭据，传递实际型号、会话和请求 ID。该层不解析、复制或序列化凭据，不刷新、不重试、不选账号、不调用管理能力。
- 原生 WorkBuddy、Trae 的协议实现留在各自包，文件逐字节不变；不创建两个内容相同的平台包装器。共用绑定只调用既有 `provider.Adapter.Stream` 的窄接口。
- 两平台非流式聚合归 `gateway.Completions.CompleteStream`，维持原 32MiB 上限和超限错误；CodeArts 原有聚合回退仍采用原行为。普通流式立即回调，不变成缓冲整个回复后输出。
- 上游分片仍先标记已观察，再捕获用量，最后交给消费者/聚合器。被上限拒绝的分片也计入观察和用量；发生部分输出后错误时不自动重放。借用分片保存前复制，原始工具参数与大整数不变。
- 凭据获取与刷新互斥、提示词恢复、总重试/超时预算、摘要编排、选号准入锁及账本继续原实现。页面、持久化 schema 6、登录、搜索、奖励接口不变。

## 性能与部署

性能对比使用基线 `9f4b100` 与本批各自编译的测试二进制，注入相同测试夹具；两平台原生协议代码逐字节相同。首轮采用机器默认 16 个逻辑 CPU，三轮交替测试中 WorkBuddy 流式、Trae 非流式的 p95 中位数分别增加 18.58%、13.07%，各轮波动较大，不能直接视为通过。

随后固定两个不同物理核（CPU 0、2），两版本均设置 `GOMAXPROCS=2`，进行七轮交替复测。每轮每种模式 40 次请求、并发 2、固定上游等待 20ms，两段 HTTP 均经过本机 socket；全部请求成功，实际上游调用次数与请求数一致，峰值并发为 2，剩余租约为零。

| 平台与模式 | 基线 p95 中位数 | 本批 p95 中位数 | 变化 |
| --- | --- | --- | --- |
| WorkBuddy 非流式 | 23.440ms | 23.752ms | +1.33% |
| WorkBuddy 流式 | 23.303ms | 23.125ms | -0.76% |
| Trae 非流式 | 22.910ms | 23.145ms | +1.03% |
| Trae 流式 | 23.025ms | 23.065ms | +0.17% |

相同绑核条件下五轮微基准的耗时变化为 -0.98%～+1.12%；每请求分配次数增加 0～1 次，不增加分片 I/O、网络轮次、锁或凭据编解码。复测未复现首轮的大幅差异，也未发现稳定超过 5% 的退化。该结果只覆盖上述并发和夹具，不代表所有负载均零开销；真实上游耗时不能用来区分这一级本地开销。原始结果保存在本机忽略目录 `artifacts/structure-m3-3/`，公开汇总见 [JSON 记录](STRUCTURE-M3-3-2026-11-01.json)。

本机用户服务已更新为 `0.3.0-structure-m3.3`，继续监听 `127.0.0.1:10088`。实际进程 cwd、版本及运行文件 hash 与已验收 Linux 产物一致（SHA-256：`5b101cef5582f840e1681bd9e45c4686a710c973549b30067660d3a90f9c6c90`）。模型目录加载完成后 `/health` 显示 4 个账号、4 个就绪、83 个模型。重启前后状态、访问恢复文件、用量账本及成长任务文件逐字节一致，schema 仍为 6，3 个分组、4 把密钥；私有备份保存在仓库外。云端未更新。
