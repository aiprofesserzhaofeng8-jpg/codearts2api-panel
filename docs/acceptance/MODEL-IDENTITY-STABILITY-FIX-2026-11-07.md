## 已处理的行为

| 问题 | 修复后行为 | 兼容边界 |
| --- | --- | --- |
| 历史跨厂商隐式别名 | gpt-4o、gpt-5、Claude 等厂商型号不再隐式解析到 GLM；真实目录条目和管理员显式别名继续可用 | 原来依赖隐式替换的请求需改用真实型号或明确配置的别名；不会继续假冒原型号。历史名字仍参与旧配置离线迁移冲突检查，避免迁移误改语义 |
| Qoder 槽位名称漂移 | 已保存统一模型和旧映射复用默认名称生成所用的目录名称校验；原生公开名称对应的槽位显示名变化时，从实时候选中排除该来源 | 其他匹配来源继续可用；全部匹配来源被排除时返回 409/model_source_identity_changed。显式平台服务入口和自定义服务名保留；显示名恢复后自动恢复资格 |
| 新配置替换上下文 | 公共及平台默认值均为 passthrough、prompt_fallback=false、sanitize=false；管理页面缺字段时采用同样默认值 | 不覆盖已有明确保存的配置；custom、恢复、清洗仍可手动启用。普通协议转换仍遵循各平台原有契约，不宣称所有 HTTP 请求字节均保持一致 |
| 客户端会话标识未识别 | 现有粘性哈希额外识别 Session_id 和 X-Conversation-Id | 顺序为 X-Session-Id、Session_id、X-Conversation-Id、body.conversation_id，最后才按首条用户内容及系统提示构造最佳努力标识。仍按密钥和公开模型隔离 |
| Pi 元数据未知时覆盖图片能力 | 同步得到未知图片能力时保留既有 input，并报告未知；新的无能力保证条目仍不会凭空声明支持图片 | 明确支持/不支持的服务端元数据照常更新。未改动本机真实 Pi 配置 |

Qoder 校验仅覆盖现有已审核映射及对应的原生公开名称，不是对任意自定义别名的底模认证。目录显示名本身也不是服务器内部实际执行型号的证明。没有按模型回复“我是谁”做自动识别。

## 仍需处理及不能保证的事项

1. WorkBuddy 服务器内部是否使用另一型号或视觉处理阶段，网关没有控制权。本批沿用既有原生能力上限：不因平台增强服务能够处理图片，就将原生文本型号声明为视觉模型。需要视觉时由客户端选择明确支持图片的独立型号。
2. Trae 当前适配器仍拒绝图片。调查到第三方 [Trae2api-cn 的 raw_client.py](https://github.com/autumnsentiment/Trae2api-cn/blob/5c87d6c309499974f5dc786ba2fe22d3c64db1cf/src/raw_client.py) 使用独立 llm_raw_chat 传输，并保留图片内容块；这是协议实现参考，不能证明当前账号、产品和凭据可用。迁移前需要验证认证、型号绑定、图片、工具和历史完整性，不能仅取消旧校验或改支持声明。
3. Kiro 图片内容位置限制尚未改变。平台增强入口、auto 与不透明槽位仍不认证底模身份；响应顶层公开型号保留协议兼容行为。
4. 现有粘性属于尽力复用，满载、失败或冷却仍可切换来源；没有新增强制来源锁定或等待队列。无稳定会话 ID 的客户端在压缩历史后仍可能改变绑定。
5. 尚未完成固定账号、固定来源、固定前缀与允许切源的缓存 A/B 实测。因此不能报告缓存命中率已改善或模型效果已恢复。
6. R2 原有两个 CodeArts 404 来源阻塞仍保留，见 [R2 验收](SOURCE-CAPABILITIES-R2-2026-11-07.md)。
