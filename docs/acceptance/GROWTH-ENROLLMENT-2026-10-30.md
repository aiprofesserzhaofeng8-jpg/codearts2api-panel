# Buddy 无需接取及执行入口恢复

日期：2026-10-30。修复提交：`c9214743aeb197d4466b3999fe7aa50d76a2d75c`，已部署至本机 10087。

## 截图问题的真实原因

以当前账号单独接取 `first_buddy`，上游返回 HTTP 200、业务 code 0，但单项结果为 `status=error`，原文 `task does not require acceptance`。这表示该任务本来就无需手动接取，不能把它归因为账号缺少前置条件。

本地有两处适配错误：给这类任务显示了「接取任务」，并将接取失败的阻止状态复用于执行/领奖，导致「解锁并领养」及批量执行也变灰。此前的通用错误说明没有区分无需接取与前置不足，容易误导。

## 修复

- WorkBuddy 将 `first_buddy` 标注为 `accept_not_required`，不信任上游传入的本地能力字段。页面不再显示接取入口，也不再将其标成未报名，批量接取跳过该任务。
- 旧页面或直接 API 仍请求接取时，服务端在发送上游写请求前返回明确的「无需接取，请直接点击解锁并领养」指引。
- 接取失败只阻止本轮重复接取，不再连带禁用真实执行和领奖；执行/领奖自身的未知结果保护、账号锁和持久化付费检查点保持生效。

## 验证与限制

成长任务后端针对性 race 测试、CodeArts/Trae/provider 回归、`go vet ./...`、Linux 构建、JS 语法，以及成长任务五套浏览器检查通过。新增浏览器用例先触发两个账号的接取前置拒绝，再在不刷新页面的情况下完成模拟领养及对话，确认操作间不会误伤禁用。

部署后使用真实账号打开页面，确认 Buddy 接取按钮消失、领养及批量执行入口可用、旧接取请求获得明确 409 指引。没有新增真实模型尝试；设置、密钥与分组不变，临时管理会话已退出。普通推理链路和其他两个平台的适配未修改。

当前账号依然是 `agreed=true`、`owned=false`，前置付费对话检查点仍为待确认。之前唯一一次真实前置对话发生响应头超时；尚无已领养或领奖的上游确认。本次解决了截图中的错误入口和禁用问题，真实领养/奖励仍未验收成功，不会删除检查点或重发付费对话来掩盖这一限制。
