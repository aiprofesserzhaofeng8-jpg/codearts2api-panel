# store

## 职责

网关全部运行期状态的唯一归宿：API 密钥、请求日志、设置、账号池，以及它们的落盘与迁移。

同时是账号池的调度者：按可用性挑下一个账号、记录成功/失败、标记熔断。

## 边界

- **只依赖 `codearts`**（持久化 `Account` / `Session` 类型）。
- **不认识 HTTP**，也不认识模型清单。

## 关键决策

- **对外只给浅拷贝，不给内部指针。** `Account` 的字段会被请求路径（`MarkAccountResult`）
  与控制台并发读写，直接交出内部指针就是数据竞争。`Session` 指针可以共享 ——
  它构造完成后不再原地修改，续期是整体替换指针。
- **落盘必须串行 + 临时文件名唯一。** 并发 `Save` 曾共用同一个 `<path>.tmp`：Windows 上
  报「文件被占用」而失败（调用方多半忽略错误 → 状态静默不落盘），Linux 上可能把写了一半的
  临时文件 rename 成正式状态文件。现在由 `saveMu` 串行化，临时文件以 `0600` 创建
  （里面是 STS 凭据与 refresh_token），fsync 后再 rename。
- **schema 带版本号，迁移就地做。** 状态文件版本高于本程序时拒绝启动并提示升级 ——
  静默降级会让新版本写的字段被旧程序丢掉。
- **结算先记追加账本，再更新可见计数。** `usage_journal.go` 统一处理三个上游与所有
  协议的结算；每条记录同步写入 `state.json.usage.jsonl`，只存请求元信息、当时价格
  和密钥哈希。已有 SSE 转发不等待中途写盘，预算预留在结算返回后才释放。
- **快照带结算序号，恢复只补检查点之后的记录。** 正常每 30 秒保存 JSON 快照，
  原子替换并同步目录后清理已保存的账本前缀。保存快照的磁盘 I/O 期间仍可追加结算，
  清理保留这些新记录。预算重置、价格修改等事务同样携带检查点，不能重复扣费或重算历史。
- **写账本失败时保留内存用量并暂停新推理。** 新请求返回 503，已经获得的有效模型响应
  保留；后续快照完整保存、账本恢复可用后自动解除暂停。完整但损坏的账本会阻止启动，
  不把无法恢复的数据当作零消耗；中途写入留下的无换行尾部按未提交记录截去。
- **旧模型名在启动时迁移。** 免费权益通道下线后，历史设置里的默认模型名在上游一律报错，
  启动时重映射到当前默认模型。

## 已知限制

- **不支持多进程并发写。** `Save` 有原子性（不会写坏），但没有读-改-写合并；
  两个进程共用一个状态文件会丢更新（last-writer-wins）。
- **备份须包含快照和旁边的账本。** 停止服务后备份最简单；运行中直接复制两份文件不构成
  一致性备份。schema v5 不允许旧版本忽略检查点，回退旧程序须恢复配套旧快照。
- **保证边界是已成功提交的结算。** 上游正在生成、最终用量尚未收到或账本写入尚未完成时
  强杀，仍可能无法核实上游消耗；此改动不会推算 Token 或重发请求补账。宿主断电和硬件
  不遵守同步语义的情况未做真实断电验收；Windows 仅同步文件，不同步目录句柄。
